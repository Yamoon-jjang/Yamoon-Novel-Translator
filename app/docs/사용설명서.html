1. 이 프로그램은

중국어 · 일본어 · 영어로 된 TXT · PDF · EPUB 소설이나 문서를 한국어로 번역합니다. 원문을 새로 쓰거나 순화하지 않고, 뜻과 수위와 문체를 그대로 옮기는 번역을 목표로 합니다. 미성년자가 관련된 성적 내용만 번역에서 제외합니다.

  • 빠짐없이 — 문단마다 번호를 붙여 보내고 같은 번호가 그대로 돌아왔는지 확인합니다. 순서가 바뀌거나 문단이 사라지지 않습니다.
  • 여러 번역 엔진 — Gemini, OpenAI, 내 PC의 로컬 LLM 중 1~3개를 골라 순서를 정합니다. 앞 엔진이 거부하거나 막은 문단은 다음 엔진이 이어서 번역합니다.
  • 같은 이름으로 — 인명·지명을 책 전체에서 같은 한국어 표기로 유지합니다. 번역을 시작할 때 자동으로 뽑아 둘 수도 있습니다.
  • 끊겨도 이어서 — 조금씩 저장하면서 번역하므로, 중간에 멈추거나 PC가 꺼져도 번역한 곳부터 이어집니다.
  • 폴더 통째로 — 폴더 안의 TXT · PDF · EPUB 파일들을 순서대로 끝까지 번역합니다.
  • PDF · EPUB도 — 글자만 꺼내(PDF는 머리글 · 쪽 번호 · 줄 끊김까지 정리) TXT와 똑같이 번역합니다 (4-4).
  • 원본 보호 — 원본 파일은 바꾸지 않고, 결과를 .ko.txt 파일로 따로 저장합니다.
v2.5에서 달라진 점
  • 번역 중지가 로컬 LLM까지 바로 멈춤 — 중지하면 Ollama가 쓰던 답도 그 자리에서 끊겨, 그래픽카드가 쓸모없는 청크를 계속 만들지 않고 다음 작업이 기다리지 않습니다 (8장).
  • 이름 표기 일괄 변경이 다른 낱말을 건드리지 않음 — 하늘 → 하늬로 바꿔도 "하늘색", "하늘나라"는 그대로 둡니다 (6-8).
  • 재정비의 의심 구간은 확인된 것만 반영 — 분량·말투·이름 변화가 의심되는데 확인 요청이 실패하면 원문을 보존하고, 나중에 그 문단만 다시 시도할 수 있습니다 (재정비).
  • 재정비 창 크기 고정 — 진행 중 안내 줄이 바뀌어도 창이 늘었다 줄었다 하지 않습니다. 창의 안내 문구는 짧게 줄이고 자세한 설명은 이 설명서에 모았습니다.

번역 속도·번역 방식·용어 추출·말투표·이어 번역 기록은 v2.41과 같습니다. 이전 버전에서 번역하던 책도 그대로 이어서 번역됩니다.

3분 요약
  1. NovelTranslator.exe 실행 → API 설정에서 Gemini 키 등록 (3장)
  2. TXT · PDF · EPUB 파일을 창에 끌어다 놓기 (4장)
  3. 번역 시작 / 계속 → 원본 옆에 파일이름.ko.txt가 생김
  4. 미번역 부분이 남으면 묻지 않고 이어서 자동으로 다시 번역합니다. 그래도 남으면 끝에 알려 줍니다 (7장)

2. 설치와 첫 실행

  1. 내려받은 압축 파일을 원하는 폴더에 풉니다. (설치 과정은 없습니다)
  2. 폴더 안의 NovelTranslator.exe를 실행합니다.
  3. 처음 실행할 때 Windows가 "PC 보호" 창을 띄우면 추가 정보 → 실행을 누릅니다. 서명하지 않은 개인 제작 프로그램이라 나오는 안내입니다. 압축을 풀기 전에 zip 파일을 오른쪽 클릭 → 속성 → 차단 해제에 체크하면 이 창이 나오지 않습니다.
  4. 바탕화면·작업 표시줄 바로가기는 처음 한 번 NovelTranslator.exe를 직접 실행한 뒤에 만드세요. 첫 실행 때 프로그램이 자기 폴더 파일의 "웹에서 받은 파일" 표시를 지워, 이후 바로가기로도 열립니다(Windows 스마트 앱 컨트롤 대응).
  5. 오른쪽 위 API 설정에서 번역 엔진을 준비합니다. (다음 장)
팁 · 오른쪽 위 환경 점검은 설정 파일과 저장 폴더가 정상인지 확인합니다. 실제 번역 요청은 보내지 않습니다.

새 버전으로 바꿀 때는 새 폴더에 압축을 풀어 쓰면 됩니다. API 키와 진행 기록은 따로 저장되어 있어 그대로 이어집니다(13장).

3. 번역 엔진 준비 (API 설정)

API 설정을 누르면 맨 위에 번역 엔진 순서, 그 아래 Gemini / OpenAI / 로컬 LLM 탭이 있습니다. 위 목록에서 엔진을 누르면 아래에 그 엔진의 탭이 열립니다.

3-1. 엔진 순서 정하기

  • 쓸 엔진에 체크합니다. 1개만 써도 되고, 2개나 3개를 함께 써도 됩니다.
  • 위로 ↑ 아래로 ↓로 순서를 정합니다. 맨 위가 주 번역 엔진이고, 아래는 순서대로 보조입니다. 보조 엔진은 앞 엔진이 막은 문단을 받아 번역하고, 앞 엔진이 한도 소진·장애로 멈추면 남은 부분을 이어서 번역합니다.
  • 메인 화면의 모델 칸은 맨 위 엔진의 모델을 보여 줍니다. OpenAI를 맨 위로 올리면 "OpenAI 모델"과 OpenAI 모델 목록이, 로컬 LLM을 올리면 "로컬 LLM 모델"과 설치된 모델 목록이 나오고, 거기서 바꾼 모델은 API 설정에도 저장됩니다.

3-2. 번역·분석·재정비 엔진 설정 구분

API 설정에서 모델을 통합 관리합니다. 번역 시 사용 엔진 · 우선순위는 Gemini·OpenAI·로컬 LLM의 번역 실행 순서입니다. 용어·말투 분석은 이름·호칭·말투표 분석을(엔진을 고르면 번역 엔진과 상관없이 그 엔진과 모델만 쓰고, 자동이면 번역에 체크한 엔진만 그 순서대로 씀), 문학적 윤문·연속성은 한국어로 번역된 소설의 문장 교정을 담당합니다. 모델은 각각 달라도 됩니다.

한국어 소설 재정비는 로컬 LLM 전용

온라인 AI는 긴 소설에서 토큰 비용, 출력 길이 제한, 긴 대기 시간, 일부 내용의 교정 거부가 발생할 수 있어 재정비는 용어·말투 분석과 문학적 윤문 엔진을 모두 로컬 LLM으로 설정해야 시작할 수 있습니다. Gemini·OpenAI·자동을 선택한 항목이 하나라도 있으면 재정비 시작이 비활성화되고 API 설정 변경을 안내합니다. 앱이 임의로 모델을 변경하지 않습니다. 로컬 LLM 역시 문맥 길이·메모리·속도의 제한이 있고 결과 품질은 보장되지 않습니다.

재정비 창은 API 설정의 분석 모델과 윤문 모델명을 읽기 전용으로 표시합니다. 재정비 창에서 별도로 엔진을 지정하거나 API 설정을 덮어쓰지 않습니다. 예를 들어 분석에 14B, 윤문에 26B 모델을 사용할 수 있습니다. 번역 시 사용 엔진 순서에는 이 제한이 적용되지 않으며 번역용 Gemini와 OpenAI 키는 그대로 유지됩니다. Ollama 등록은 11-1절을 참조하세요.

3-3. Gemini 키 등록

  1. 웹 브라우저에서 aistudio.google.com/apikey 에 Google 계정으로 들어가 API 키 만들기로 키를 받습니다.
  2. Gemini 탭에서 키 추가 → 키를 붙여넣기 → 구분용 이름(선택) → 프로젝트 그룹을 입력합니다. 새 키는 자동으로 P1, P2…처럼 따로 잡히니 다른 프로젝트에서 만든 키면 그대로 두고, 이미 등록한 키와 같은 프로젝트의 키일 때만 그 그룹 이름을 적으세요. 이미 등록한 키는 표의 "프로젝트 그룹" 칸을 두 번 클릭해 고칠 수 있습니다.
  3. Gemini 키 표의 등급에서 Google AI Studio에서 직접 확인한 무료 / 유료를 선택합니다. 같은 프로젝트 그룹의 키는 같은 등급으로 설정해야 저장할 수 있습니다. 미지정은 기존 키와 호환되며 무료 사용을 보장하지 않습니다. 이 등급은 Google로부터 자동으로 조회하는 정보가 아닙니다.
  4. 키를 선택하고 선택 키 연결 테스트로 확인합니다.
  5. 같은 탭의 Gemini 모델 ID에서 모델을 고릅니다(기본 Gemini 3.1 Flash Lite). 메인 화면의 Gemini 모델 칸과 같은 설정이라, Gemini를 보조 엔진으로 둘 때는 여기서 바꾸면 됩니다.

3-3. Gemini 키는 이렇게 쓰입니다

핵심 · Google의 한도는 키가 아니라 프로젝트 단위로 계산됩니다. 같은 프로젝트에 키 5개를 만들어도 해당 프로젝트의 할당량이 5배로 늘어나지 않습니다. 보통 프로젝트당 키 1개면 충분합니다. 별개 프로젝트의 제한도 Google 정책에 따라 다른 상위 제한의 영향을 받을 수 있습니다.
  • 평소에는 맨 위 키 하나만 계속 씁니다. 키를 돌아가며 쓰지 않습니다. 나머지 키는 예비입니다.
  • 키가 무효·차단되면 그 키만 끄고 아래의 다음 키로 넘어갑니다.
  • 프로젝트가 분당 한도·하루 한도에 걸리면, 같은 프로젝트 그룹의 키를 모두 함께 잠시 쉬게 하고 다른 프로젝트 그룹의 키로 넘어갑니다. 같은 프로젝트의 다른 키로 바꿔도 한도는 그대로이기 때문입니다.
  • 다른 프로젝트도 없으면 다음 엔진으로 이어 가거나, 한도가 풀릴 때까지 기다렸다가 자동으로 이어 번역합니다.
등록 예결과
프로젝트 2개 × 키 5개, 그룹 P1 ×5 · P2 ×5평소 P1의 첫 키만 사용. P1이 한도에 걸리면 P2의 첫 키로. 실제 한도는 프로젝트 2개 몫.
같은 키 구성인데 그룹이 모두 default10개가 한 프로젝트로 취급되어, 한도에 걸리면 10개가 함께 쉽니다. 다른 프로젝트로 넘어가지 못합니다.
프로젝트 2개 × 키 1개씩, 그룹 P1 · P2첫 번째 예와 같은 효과. 프로젝트마다 키는 1개면 충분합니다.
무료 A → 무료 B → 유료 C, 각각 키 1개A를 우선 사용하고, A 프로젝트가 제한되면 B, 모두 제한되면 사용 가능한 C로 자동 전환합니다. 전환 확인 창은 뜨지 않으며 C에서는 유료 사용료가 발생할 수 있습니다.

번역 중 API 상태 줄은 선택된 프로젝트 그룹과 사용자가 지정한 무료/유료/등급 미지정을 표시합니다. 전체 API 키 원문은 보여 주지 않습니다. 같은 모델이면 무료와 유료 프로젝트의 기본 번역 품질은 같으며, 속도 차이는 주로 프로젝트 요청 제한과 대기 시간에 생깁니다. 무료 우선을 원하면 무료 키들을 위에, 유료 키를 맨 아래에 배치하세요. 유료 프로젝트를 절대로 쓰지 않으려면 유료 키의 사용 체크를 해제하세요.

한도 숫자 · 분당·하루 요청 한도는 모델, 결제 등록 여부(무료/유료 등급), 계정에 따라 다르고 Google이 바꾸기도 합니다. 정확한 값은 Google AI Studio(aistudio.google.com)에서 자기 프로젝트의 한도 화면으로 확인하세요. 이 프로그램은 요청을 한 번에 하나씩 보내므로 실제 속도가 분당 한도를 넘는 일은 드물고, 넘더라도 스스로 속도를 낮춥니다(부록 B).

3-5. 로컬 LLM (선택)

내 PC에서 돌아가는 무료 번역 엔진입니다. 준비 방법은 11장을 보세요.

4. 번역하기

끌어다 놓기 · 탐색기에서 TXT · PDF · EPUB 파일이나 폴더를 프로그램 창(원문 창 포함)에 끌어다 놓아도 열립니다.
  • TXT · PDF · EPUB 파일 하나 → 파일 하나 번역 (4-1, PDF · EPUB은 4-4)
  • 폴더 하나 → 폴더 번역 (4-3)
  • TXT · PDF · EPUB 파일 여러 개(Ctrl·Shift로 골라서) → 폴더 번역처럼 차례로 번역하되, 끌어다 놓은 파일만 번역합니다. 결과는 그 파일들이 있는 폴더의 한국어_번역에 저장됩니다.
번역 중에는 끌어다 놓아도 열리지 않습니다(진행 중인 작업 보호).

4-1. 파일 하나

  1. TXT·PDF·EPUB 파일 선택으로 파일을 엽니다. 원문이 원문 탭에 보입니다. PDF · EPUB은 4-4를 보세요.
  2. 원문 언어와 번역 방식(기본: 균형)을 확인합니다. 파일을 열면 원문의 문자를 보고 중국어·일본어·영어를 자동으로 맞춥니다(상태 줄에 "원문 언어를 ○○로 자동 설정했습니다"가 표시됨). 판별이 확실하지 않거나, 그 파일에 전에 다른 언어를 직접 골라 둔 적이 있으면 현재 설정을 그대로 둡니다. 다르면 원문 언어 칸에서 바꾸면 됩니다.
  3. 아래 번역 시작 / 계속을 누릅니다. 진행 중에는 번역 결과를 눌러 번역되는 한국어를 실시간으로 볼 수 있습니다.

번역이 끝나면 원본과 같은 폴더(출력 폴더 지정으로 폴더를 정했다면 그 폴더)에 파일이름.ko.txt가 생깁니다. 결과 폴더 열기로 바로 열 수 있습니다.

4-2. 붙여넣은 글

파일 없이도 됩니다. 원문 탭의 큰 창에 글을 붙여넣고(Ctrl+V) 번역 시작 / 계속을 누르세요.

  • 파일을 연 뒤에 끝에 글을 이어 붙이거나 일부를 고쳐도 됩니다. 원본 파일은 바뀌지 않고, 이미 번역한 부분은 다시 요청하지 않습니다.
  • 끝나면 같은 창이 번역 결과 보기로 바뀝니다. 원문 / 번역 결과로 오가고, 결과 복사 · 결과 저장을 쓸 수 있습니다.
  • 새 파일을 열면 붙여넣은 글은 그 파일 내용으로 바뀝니다.
  • 파일 없이 붙여넣은 글의 결과는 지정한 출력 폴더, 지정하지 않았다면 문서\야문 Novel Translator 폴더에 저장됩니다.

4-3. 폴더 통째로

  1. 폴더 선택으로 폴더를 고릅니다. 작업 목록에 폴더 안의 TXT · PDF · EPUB 파일이 이름 순서대로 나옵니다.
  2. 폴더 옵션을 고릅니다.
    • 하위 폴더 포함 — 안쪽 폴더의 TXT · PDF · EPUB까지 번역합니다.
    • 각 파일 독립 작품 (기본) — 파일마다 다른 작품으로 봅니다.
    • 한 작품의 연속 파일 — 1권, 2권처럼 이어진 작품이면 이것을 고르세요. 앞 파일의 마지막 흐름을 다음 파일에 넘겨줍니다.
  3. 번역 시작 / 계속을 누르면 파일을 하나씩 끝까지 번역합니다.

결과는 원본 폴더\한국어_번역\에 같은 하위 폴더 구조로 저장되고, 마지막에 번역_요약.txt가 생깁니다(파일별 결과, 자동 재시도 뒤에도 남은 미번역 상세, 폴더 전체 추정 비용).

무인 진행 · 폴더 번역은 확인 창 없이 끝까지 갑니다. 요청 한도나 네트워크 문제로 멈추면 1분 / 2분 / 15분 기다렸다가 같은 파일을 자동으로 이어 번역하고, 읽을 수 없는 파일이나 설정 오류가 난 파일(글자 없는 스캔 PDF · 그림만 있는 EPUB 포함)은 건너뛰고 다음 파일로 넘어갑니다. 진행을 멈추는 것은 사용자의 번역 중지뿐입니다.

4-4. PDF · EPUB 파일

PDF와 EPUB(전자책)도 TXT처럼 열고 번역합니다. 열면 글자만 꺼내 원문 창에 넣고, 그다음은 TXT와 똑같이 번역합니다(용어집 · 말투표 · 이어 번역 · 미완료 재시도 모두 같음). 원본 파일은 바뀌지 않습니다. 꺼낸 글은 원문 창에서 확인하고, 필요하면 고친 뒤 번역해도 됩니다.

PDF

  • 꺼낸 글은 정리됩니다 — 쪽마다 반복되는 머리글 · 꼬리글(책 제목, 장 제목 등)과 쪽 번호는 지우고, 쪽 너비 때문에 끊긴 줄은 문단으로 다시 잇습니다. 장 제목(第一章, Chapter 1 등)은 따로 한 줄로 둡니다.
  • PDF 모양은 따라가지 않습니다 — 글자 배치 · 그림 · 표는 옮기지 않고 본문 글만 번역합니다. 2단 편집이나 표 · 각주가 많은 PDF는 문장 순서가 섞일 수 있으니 원문 창에서 한 번 훑어보세요.
  • 스캔 PDF — 종이를 찍어 만든 PDF처럼 글자 정보가 없는 PDF는 "문자 인식(OCR)이 필요한 PDF"라고 알려 주고 열지 않습니다. 문자 인식(OCR) 프로그램으로 글자가 들어간 PDF나 TXT를 만든 뒤 여세요.
  • 암호가 걸린 PDF — 열 때 암호가 필요하거나 AES 보안이 걸린 PDF는 글자를 꺼낼 수 없습니다. PDF 보기 프로그램에서 보안을 푼 PDF로 다시 저장한 뒤 여세요.

EPUB

  • 책의 읽는 순서대로 본문을 꺼냅니다. 문단과 장 제목은 원래 구분된 그대로 쓰고, 일본어 루비(후리가나) 읽기 표기는 빼고 본문 글자만 남깁니다. 그림 · 글꼴 · 꾸밈은 옮기지 않습니다.
  • 글자가 없는 EPUB(그림으로만 된 만화 등)은 번역할 글이 없다고 알려 주고 열지 않습니다.
  • 복제 방지(DRM)가 걸린 EPUB은 글자를 꺼낼 수 없습니다. 구매한 서점의 앱에서만 읽을 수 있는 파일입니다.

TXT 인코딩 설정은 PDF · EPUB에 적용되지 않습니다(글자를 그대로 꺼냄). 폴더 번역에서 열 수 없는 PDF · EPUB은 그 파일만 건너뛰고 다음 파일로 넘어갑니다.

저장 — PDF · EPUB으로 연 파일도 자동 저장은 TXT와 같습니다: 파일이름.ko.txt, 덜 끝났으면 파일이름.ko.partial.txt, 출력 폴더 지정과 이어 번역도 그대로입니다(폴더 번역도 같음). 같은 폴더에 이름이 같은 TXT · PDF · EPUB이 함께 있으면(책.txt와 책.pdf) 서로 덮어쓰지 않도록 PDF · EPUB 쪽 결과는 책.pdf.ko.txt · 책.epub.ko.txt로 저장됩니다.

PDF나 EPUB으로 받고 싶으면 번역이 끝난 뒤 결과 저장에서 파일 형식을 고르세요(기본은 TXT). 원본 모양을 따라 하지 않고 새로 짠 읽기용 파일을 만듭니다.

  • PDF로 연 파일 → PDF · 읽기용: 한글 글꼴(맑은 고딕), A5 크기, 문단 간격, 장 제목은 새 쪽에서 시작, 아래쪽 가운데 쪽 번호. 파일이름.ko.pdf
  • EPUB으로 연 파일 → EPUB · 읽기용: 장 제목마다 새 장으로 나누고 목차를 붙인 전자책(EPUB 3), 문단 간격. 글꼴은 전자책 앱의 한글 글꼴을 쓰고, 쪽 번호는 전자책 앱이 매깁니다. 파일이름.ko.epub
  • TXT로 연 파일은 지금처럼 TXT로만 저장합니다.

6. 이름 · 용어 · 말투 · 번역 지침

6-1. 확정 용어집

확정 용어집에 "원문 → 한국어"를 적어 두면 모든 엔진이 책 전체에서 그 표기를 지킵니다. 엔진이 바뀌어도 같습니다. 용어 추가, TSV 가져오기 / TSV 내보내기로 관리합니다.

확정 용어 충돌 일괄 검토와 고정

새 분석에서 이미 확정한 원문 용어와 다른 표기가 나오면, 아직 고정하지 않은 충돌 용어들을 하나의 검토창에 모읍니다. 예전처럼 모든 용어를 Yes/No 한 번으로 바꾸지 않습니다.

  1. 목록에서 원문, 기존 표기, 새 제안을 비교하세요. 기본 결정은 기존 유지·고정입니다. 바꾸고 싶은 항목만 새 제안·고정을 선택합니다.
  2. 목록이 길면 검색하고 세로 스크롤하세요. 열이 길면 가로 스크롤이나 셀에 마우스를 올려 전체 표기를 확인할 수 있습니다. 창은 화면 사용 가능 영역을 넘지 않도록 제한됩니다.
  3. 전체 기존 유지 또는 전체 새 제안은 현재 검색 결과 중 보이는 항목에 적용됩니다. 선택 사항 적용으로 저장하고 취소하면 기존 확정 표기는 유지됩니다.
한 번 고정한 표기는 자동 제안으로 바뀌지 않습니다.

예: 秦岚 → 진란을 고정한 다음 다른 엔진이 친란이라고 제안해도 반복해서 묻지 않습니다. 고정은 수동 편집 금지가 아닙니다. 용어집의 한국어 표기를 직접 친란으로 바꾸면 새 값으로 고정됩니다. 용어를 삭제하면 고정 기록도 정리됩니다. 작품별 고정 기록은 작업 데이터에 저장되며 다른 작품의 공용 용어집까지 자동으로 덮어쓰지는 않습니다.

이름 표기 방식 변경 후 사용자가 새 방식으로 다시 추출을 명시적으로 승인하면 기존 표기를 재추출한 값으로 바꿀 수 있습니다. 자동 재제안과 사용자가 지시한 재추출을 구분합니다.

내 공용 용어집 — 책마다 쌓아 다음 책에도

"공용 용어집 사용"(기본 켜짐)이면 번역을 시작할 때(그리고 끝날 때) 그 책의 확정 용어 중 공용 용어집에 아직 없는 것만 언어별로 쌓아 둡니다. 번역 전에 미리 쌓고 싶으면 공용 용어집 창 위쪽의 "새로 쌓일 항목 N개"를 확인하고 지금 추가 → 저장을 누르세요.

  • 중복은 쌓지 않습니다. 이미 있는 원문 용어는 처음 쌓인 표기를 그대로 두고 바꾸지 않습니다.
  • 쓸모없는 것은 쌓지 않습니다. 한자가 남은 표기, 이름이 아닌 일반 단어(公司 → 회사 같은 빨간 항목), 한 글자 원문, 한글이 없는 표기는 걸러 냅니다.
  • 새 책에서는 인명·용어를 추출할 때 본문에 두 번 이상 나오는 공용 항목(두 글자 항목은 다섯 번 이상)을 후보로 함께 보내고, 분석 엔진이 이 책에서도 이름·용어라고 확인한 것만 확정 용어집에 넣습니다(공용의 한국어 표기 그대로 — 속편에서 이름이 유지됨). 다른 책에서 이름이었던 慢慢(천천히)·微微(살짝)처럼 이 책에서는 일반 낱말인 항목은 들어오지 않습니다. 작업 기록에 "공용 용어집 항목 N개 중 확인된 M개 가져옴"이 남습니다. 나머지는 번역 중 그 덩어리에 나올 때만 참고 힌트로 씁니다.
  • 내장 언어팩 힌트는 원문에 그 단어가 따로 나올 때만 보냅니다. 主人公 안의 主人, 在下面 안의 在下처럼 다른 말의 일부일 뿐인 자리는 제외합니다(제외 목록: 프로그램 폴더의 config/lexicon_exclude.json).
  • 힌트는 내장 언어팩보다 뒤입니다. 예를 들어 公公처럼 문맥에 따라 시아버지·환관으로 갈리는 말은 언어팩의 안내가 우선합니다.
  • 공용 용어집을 누르면 쌓인 목록을 보고, 찾고, 고치고, 지울 수 있습니다. 공용 용어집을 바꿔도 번역 중인 책을 다시 번역하지 않습니다.
  • 언어별 최대 5,000개까지 쌓입니다. 가득 차면 버튼에 "가득 참"이 붙고, 작업 기록과 공용 용어집 창에 "정리하세요" 안내가 나옵니다. 틀렸거나 더 쓰지 않을 항목을 골라 선택 삭제 → 저장하면 다시 쌓이기 시작합니다.

6-2. 이름 표기 방식 (한자독음 / 중국어 발음)

중국어 원문은 확정 용어집 탭 맨 위의 중국 인명 표기에서 고릅니다(언어별 설정과 같은 설정). 기본은 한국 한자음(左京 → 좌경, 李萱诗 → 이훤시)이고, 현대 중국어 발음(左京 → 쭤징)이나 자동으로 바꿀 수 있습니다. 자동 추출과 번역 모두 이 방식을 따릅니다.

확정 용어집은 이 설정보다 우선합니다. 그래서 이미 용어집에 이름이 있는 상태에서 표기 방식을 바꾸면 "새 방식으로 다시 추출할까요?"라고 묻고, 새 방식으로 다시 추출을 누르면 같은 원문 용어의 표기를 새로 뽑은 것으로 바꿉니다.

6-3. 인명·용어 자동 추출

  • 인명·용어 자동 추출은 원문에서 자주 나오는 단어 목록만(본문 문장은 보내지 않고) 선택한 분석 엔진에 보내, 이름·지명·고유 용어와 한국어 표기를 제안받습니다. 엔진에 오류가 나거나 유효한 항목이 없으면 다른 준비된 엔진으로 재시도할 수 있어 시간이 더 걸릴 수 있습니다.
  • "번역 시작 시 먼저 자동 추출"(기본 켜짐)이면 새 파일이나 붙여넣은 글을 처음 번역할 때 자동으로 한 번 실행하고, 새 항목만 용어집에 더한 뒤 번역을 시작합니다. 더해진 항목은 상태 / 오류 기록에 표시됩니다.
  • 이전에 번역하던 파일을 이어 번역하는데 용어집이 비어 있으면 추출 후 처음부터 번역 / 용어집 없이 이어서 번역 중에서 고르게 묻습니다. 이미 번역한 적이 있는 파일은 자동 추출을 하지 않습니다(아래 6-8).
  • 로컬 LLM 등 일부 모델은 이름 뒤에 동사·명사가 붙은 구절(예: 陈屿放 → 진서가 놓다, 沈疏影身 → 심소영의 몸)을 용어로 돌려주기도 합니다. 프로그램은 한국어 표기가 "이름 + 띄어쓰기" 또는 "이름 + 조사(가·이·의·를…) + 띄어쓰기" 형태인 항목을 자동으로 빼고, 陈屿明 → 진서명, 陈家村 → 진가촌처럼 한 단어로 쓰인 진짜 이름·지명은 그대로 둡니다. 이전에 이미 들어간 구절 항목은 인물 말투표의 인물 목록에서도 제외되며, 용어집에서는 직접 골라 선택 삭제하세요.
  • 자동 제안이므로 틀린 표기는 고치거나 지우세요. 한국어 표기에 한자가 남은 항목(예: 郝장화)이나 이름이 아닌 일반 단어(예: 公司 → 회사)는 연한 빨간색으로 표시되고, 번역을 시작할 때 상태 / 오류 기록에도 알려 줍니다.
  • 번역 중에도 용어집·작품 메모·원문 창은 스크롤해서 볼 수 있습니다(고치기만 막힙니다).

6-4. 인물 말투표

중국어·영어에는 존댓말 문법이 거의 없어서, 모델이 덩어리마다 "이 둘은 어떤 사이인가"를 짐작합니다. 그래서 같은 두 사람의 말투가 반말이었다가 존댓말이었다가 흔들리기 쉽습니다. 인물 말투 탭의 표는 누가 누구에게 어떤 말투를 쓰는지를 정해 두고, 매 요청에 함께 보내 그 두 사람의 말투를 책 전체에서 고정합니다.

화자상대말투관계·메모
좌경이훤시해요체어머니
이훤시좌경반말아들
제자장문인합쇼체스승
  • 자동으로 만들어집니다. "번역 시작 시 자동 생성"(기본 켜짐)이면, 표가 비어 있을 때 번역을 시작하며 한 번 만듭니다. 확정 용어집의 인물 이름과, 책 전체에서 고르게 고른 대사 약 6천 자를 API 설정에서 선택한 말투 분석 엔진에 보내 정합니다(대사 묶음별로 여러 요청이 발생할 수 있음). 생성된 결과는 확인하고 필요한 경우 수정하세요.
  • 만드는 동안 아래 상태줄과 API 상태에 지금 어느 엔진에 묻는 중인지와 경과 시간이 표시됩니다. 대사를 실제로 보내므로 엔진이 거부하면 다음 엔진(예: 로컬 LLM)으로 넘어가 시간이 더 걸릴 수 있습니다. 기다리기 싫으면 이때 말투표 건너뛰고 번역 시작(번역 시작 버튼 자리)을 누르세요. 바로 번역이 시작되고, 말투표는 나중에 말투표 자동 생성으로 만들 수 있습니다. 인물 말투 탭의 말투표 생성 취소는 번역도 시작하지 않고 멈추며, 다음에 번역을 시작하면 다시 만듭니다.
  • 대사 표본은 호칭(妈·师父·老公·さん 등)이 들어간 대사를 우선 고르고, 세 묶음으로 나눠 보냅니다. 엔진이 어떤 묶음을 거부(성인 장면 등)하면 그 묶음만 엔진 순서대로 다음 엔진(OpenAI·로컬 LLM)이 맡고, 나머지 묶음의 결과는 그대로 씁니다. 대사를 고치거나 가리지는 않습니다.
  • 인명·용어 추출은 끝날 때마다 "답에 든 항목 N개 중 M개 사용 · 걸러 냄: 후보 목록에 없는 원문 · 한국어 표기 문제 · 일반 낱말 …"을 작업 기록에 남깁니다. 모델이 답을 목록이나 종류별 묶음으로 쓰거나 표기 뒤에 원문을 괄호로 붙여도(진란(秦岚)) 읽습니다.
  • 1인칭 소설(서술이 "我/僕/I"인 회고록·가족 이야기)은 나(1인칭 화자)와 대사에 자주 나오는 가족·호칭(엄마·아빠·오빠·형·언니·누나·남편·아내·사부·선생님 등)도 말투표 인물로 함께 씁니다. 그래서 이름 없는 "나 → 엄마: 해요체" 같은 관계도 만들 수 있습니다. 이 호칭들은 확정 용어집에는 넣지 않습니다(번역에서 억지로 고정되지 않음). "나"의 관계 메모(모자·모녀 등)로 화자의 성별이 정해지면 "언니·누나", "오빠·형"은 화자에게 맞는 하나로 바뀌고 번역에도 그 호칭 규칙이 함께 갑니다(17-3).
  • 로컬 LLM에는 말투표 답을 JSON으로 받고, 답의 모양이 조금 달라도(띄어쓰기·화살표·쉼표·원문 괄호·"존대" 같은 표현) 알아서 읽습니다. 인물이 목록에 있는지, 말투가 여섯 가지 중 하나인지는 그대로 엄격하게 확인합니다. 쓸 수 없는 답이 오면 그 답의 앞부분이 작업 기록에 남고, 전체는 데이터 폴더의 logs\analysis_answers.txt에 저장됩니다.
  • 모델에게 보여 주는 인물은 확정 용어집 가운데 이 책의 대사에 가장 많이 나오는 최대 60명입니다(표의 순서와 무관 — 지명·문파처럼 대사에 거의 안 나오는 항목은 뒤로 밀림). 로컬 LLM의 답은 표 하나에 충분한 길이로 제한하고, 답이 길어져 잘리거나 같은 말을 반복해도 그때까지 나온 올바른 줄은 그대로 씁니다.
  • 대사에서 관계가 분명한 쌍만 넣고, 모르는 인물이나 엉뚱한 말투는 걸러 냅니다. 확실한 관계를 못 찾거나 모든 엔진이 거부하면 표 없이 그대로 번역을 시작합니다. 성인물이라면 API 설정의 용어·말투 분석 엔진을 로컬 LLM(검열 해제 모델)으로 고르세요.
  • 인명·용어 추출과 말투표 만들기는 직접 누른 경우에도 시작 · 엔진마다 실패한 이유 · 결과와 걸린 시간이 상태 / 오류 기록에 남습니다(번역 시작 때 자동으로 만든 경우는 번역이 시작될 때 함께 기록).
  • 틀린 줄은 말투 칸을 클릭해 목록에서 고르거나 지우면 됩니다(실수로 바뀌지 않도록 마우스 휠로는 바뀌지 않고, 휠은 표를 스크롤합니다). 고쳐도 처음부터 다시 번역하지 않고 다음 요청부터 적용됩니다. 말투표 자동 생성으로 언제든 다시 만들 수 있습니다.
  • 말투: 반말(친구·연인·아랫사람) · 해요체(부드러운 존댓말) · 합쇼체(격식 존댓말, 윗사람·스승·임금) · 하오체·하게체·해라체(무협·사극의 예스러운 말투).
  • 대사마다 누가 말하는지는 여전히 모델이 문맥으로 판단합니다. 말하는 사람이 생략된 대사가 많은 글에서는 완벽하지 않지만, 같은 두 사람의 말투가 덩어리마다 바뀌는 일은 크게 줄어듭니다.
  • 확정 용어집의 인물 이름과 1인칭 화자·가족 호칭을 합쳐 둘 이상 있어야 만들 수 있습니다(공용 용어집 항목은 추출에서 확인되어 확정 용어집에 들어온 것만 씁니다). 원문에 이름이 있어도 인물 후보로 식별되지 않으면 결과가 비어 있을 수 있습니다.

6-5. 작품 메모

"A와 B는 남매", "주인공은 반말을 쓴다", "무협 세계관" 같은 내용을 적어 두면 모든 요청에 함께 전달됩니다. 앞 문맥(최대 5,000자)보다 먼 내용을 모델에게 기억시키는 방법입니다.

6-6. 내 번역 지침

언어별 설정 탭의 내 번역 지침 칸에 원하는 번역 방식을 한국어로 적어 두면(예: "대사는 자연스러운 구어체", "남자 주인공은 반말"), 그 언어의 모든 책에서 매 요청에 함께 보냅니다. profiles 폴더의 파일을 직접 고칠 필요가 없습니다.

  • 자동 저장되고(최대 3,000자), 번역 중이어도 다음 요청부터 적용됩니다. 칸이 좁으면 크게 편집을 눌러 큰 창에서 고치세요.
  • 원문을 빠짐없이 그대로 옮기기, 문단 번호, 확정 용어집, 미성년자 관련 성적 내용 제외 같은 기본 규칙이 지침보다 우선합니다.
  • 지침을 얼마나 잘 따르는지는 모델에 따라 다릅니다. Flash Lite 같은 저가 모델은 긴 지침을 세밀하게 따르지 못하는 일이 많습니다.

6-7. 문장 스타일 — 보통 / 자연스럽게 (시험)

언어별 설정 탭의 문장 스타일에서 고릅니다. 중국어·일본어·영어마다 따로 저장되고, 기본은 자연스럽게입니다.

  • 보통: 지금까지와 똑같이 번역합니다.
  • 자연스럽게: 원문의 어순과 문장 수를 따르지 않고, 한국 사람이 읽을 때 어색하지 않은 소설 문장으로 번역하게 합니다. "그녀는…", "~것이었다", "~에 의해" 같은 번역투를 피하고, 문장을 나누거나 합치는 것을 허용합니다. 내용·수위·누가 누구에게 무엇을 했는지는 그대로 옮깁니다.
  • 추가 요청 없이 같은 번역 요청 안에서 적용되므로 요금이 늘지 않고, 원문 수위 그대로 옮기라는 기본 지시도 그대로입니다.
  • 바꾸면 바로 적용됩니다. 번역 중에 바꾸면 진행 중인 번역의 다음 청크부터 새 스타일로 번역하고(지금 요청 중인 청크는 시작한 스타일로 마무리), 작업 기록에 "문장 스타일 변경 · 청크 N부터"가 남습니다. 번역 중인 책을 처음부터 다시 번역하지는 않습니다. 이미 번역된 부분까지 바꾸려면 처음부터 다시를 누르세요.
  • 번역이 끝나면 작업 기록에 "문장 점검 · 번역투 표현 N개 (한글 1,000자당 N)"와 미번역 여부가 나옵니다. 같은 장을 두 설정으로 번역해 숫자와 읽는 느낌을 비교해 보세요(점검은 프로그램이 직접 세므로 요금이 들지 않습니다).
  • 일반 문서 번역에는 쓰이지 않습니다(문서는 항상 정확한 문서 문체).

6-8. 바꾸면 처음부터 다시 번역되는 설정

이어 번역은 "같은 원문을 같은 설정으로" 번역한 결과만 다시 씁니다. 그래서 번역 내용 자체를 바꾸는 설정을 고치면 새 작업으로 보고 처음부터 번역합니다.

v2.5 · 이름으로 시작하는 다른 낱말은 그대로

이름 바로 뒤에 붙은 글자를 보고 그 자리가 정말 이름인지 가립니다. 뒤에 조사·어미(은/는, 이/가, 을/를, 의, 도, 만, 에게, 께서, 한테, 처럼, 보다, 까지, 부터, 마저, 조차, 였다 …)나 붙여 쓴 호칭(님, 씨, 네, 들, 군, 양, 형, 언니, 누나, 오빠, 선배, 사형·사부, 공자, 소저, 낭자, 대인, 부인, 장군, 도령, 전하 …)이 오면 이름으로 보고 바꿉니다. 그 밖의 글자가 붙어 있으면 다른 낱말의 일부로 보고 그대로 둡니다.

내 번역 지침은 이미 번역된 부분까지 바꾸지는 않습니다. 앞부분까지 새 지침으로 바꾸려면 처음부터 다시를 누르세요.

한국어 소설 재정비: 번역문을 자연스러운 소설로

재정비는 중국어·일본어·영어를 새로 번역하는 기능이 아닙니다. 이미 번역된 한국어 TXT의 직역투, 어순, 조사, 어미, 문장 연결과 대사 흐름을 적극적으로 다듬습니다. 문단 안에서는 문장을 합치거나 나눌 수 있지만 줄거리·인물 관계·핵심 사건과 사실은 유지합니다.

  1. API 설정에서 용어·말투 분석과 문학적 윤문·연속성 모두 로컬 LLM을 지정하고 Ollama 등록 모델을 각각 고릅니다. 분석에 12B/14B, 윤문에 26B 같은 다른 크기를 설정해도 됩니다.
  2. Ollama 실행 상태, ollama list의 등록 모델, 앱의 목록 불러오기 및 연결 테스트를 확인합니다.
  3. 한국어 소설 재정비를 열어 한국어 TXT를 고릅니다. 결과는 출력 폴더를 지정했다면 그 폴더, 아니면 원본 옆에 저장됩니다. 중간에 멈춘 재정비는 파일 이름을 바꾸거나 옮겨도 내용이 같으면 이어서 진행됩니다. 분석·윤문 모델은 읽기 전용으로 표시됩니다. 시작 후 진행 상황과 결과 파일을 확인합니다.
  4. 완료 시 총 소요 시간과 실제 변경 문단, 원문과 동일한 문단, 미교정 원문 보존을 구분해 표시합니다. 완료 수가 실제 개선 품질을 보증하는 것은 아니므로 결과 문장을 비교하세요.
엔진별 속도 비교

재정비가 끝나면 창에 총 소요 시간이 나오고, 결과 옆의 검토 기록 파일(….refined.txt.review.txt) 둘째 줄에도 소요 시간 · 윤문 모델이, 셋째 줄에 기준표 출처(번역 기록, 또는 샘플 분석과 그 분석 모델)가 기록됩니다. 같은 TXT를 12B·26B 등 다른 모델로 재정비해 이 줄을 비교하면 됩니다. 중간에 재정비 창의 "안전 중지"로 멈춘 뒤 같은 TXT와 엔진으로 이어서 하면 소요 시간도 합산됩니다.

기준표: 번역할 때의 말투표를 그대로

재정비는 모든 요청에 인물 말투와 이름을 담은 기준표를 함께 보냅니다. 이 앱으로 번역한 결과 TXT라면 번역할 때 실제로 쓴 인물 말투표와 확정 이름·용어를 그대로 기준표로 쓰므로, 따로 분석하지 않고 번역과 말투가 어긋나지 않습니다. 내용이 같으면 파일 이름을 바꾸거나 옮겨도 찾습니다. 번역 기록이 없는 TXT(다른 번역기 결과, 이 기능이 생기기 전에 번역한 파일)는 시작할 때 용어·말투 분석 엔진으로 앞·중간·끝부분을 샘플 분석해 기준표를 만듭니다. 재정비 창에 어느 쪽을 쓰는지 나오고 기준표 보기로 내용을 볼 수 있으며, 검토 기록 끝에도 남습니다. 번역 기록의 말투를 고치려면 번역 화면의 인물 말투 탭에서 고친 뒤 다시 번역하세요.

바뀌면 안 되는 것

윤문은 문장을 적극적으로 다듬되 대사의 존댓말·반말, 호칭, 이름 표기, 표현 수위는 바꾸지 않게 요청합니다. 분량이 크게 달라졌거나, 대사의 존댓말↔반말이 바뀌었거나, 확정 이름이 사라진 구간은 한 번 더 원고와 비교해 확인하고, 문제가 있으면 원문을 그대로 둡니다. 번역에서 남은 한자·가나는 한국어로 옮기도록 요청하며, 완료 창과 검토 기록에 재정비 전·후의 남은 문단 수가 나옵니다.

못 다듬은 문단만 다시

끝난 뒤 거부·검증 실패로 원문을 둔 문단이 있으면, 같은 TXT로 다시 재정비 시작을 누르세요. "보존한 문단만 다시 시도"를 물어보고, 이미 다듬은 문단은 그대로 둔 채 그 문단만 다시 요청해 같은 결과 파일을 갱신합니다. 결과 파일을 손으로 고쳤다면 덮어쓰지 않습니다. 분석 모델만 바꿔도 진행분은 이어서 씁니다.

거부·검증 오류의 처리

Ollama에서는 재정비 요청도 번역과 같이 모든 문단 ID가 반드시 들어간 형식(구조화 출력)으로 답을 받으므로, 모델이 문단을 빠뜨리거나 합칠 수 없습니다. 그래도 문단 하나가 빠지면 나머지 교정문은 살리고 빠진 문단과 바로 앞 문단만 한 문단씩 다시 요청합니다. 모델이 거부하면 그 문단은 원문을 보존합니다. 일부 문단만 거부되고 다른 문단이 독립적으로 검증된 경우 정상 교정문은 살립니다. v2.5부터 연속성 확인이 필요한 구간(분량 변화 · 존댓말↔반말 변화 · 확정 이름이 사라짐)에서 확인 요청 자체가 실패하면(모델 오류 · 시간 초과 · 서버 끊김), 확인하지 못한 윤문을 결과에 넣지 않고 원문을 보존합니다. 검토 기록에는 "연속성 검토 실패(분량 변화) · 원문 보존"처럼 이유가 남고, 같은 TXT로 다시 재정비 시작을 누르면 "보존한 문단만 다시 시도"로 그 문단만 다시 다듬고 다시 확인합니다. v2.41까지는 이런 경우 확인하지 못한 윤문을 그대로 두고 "검토 미완료"만 기록했는데, 줄어든 윤문(내용이 빠졌을 수 있는 문장)이 결과에 남을 수 있어 원문 충실성을 우선하도록 바꾸었습니다. 확인이 필요 없는 구간(분량·말투·이름이 그대로인 구간)은 지금처럼 확인 요청 없이 바로 저장하므로 속도는 그대로입니다. "안전 중지"를 누른 순간 확인을 기다리던 의심 구간도 저장하지 않고 남겨 두었다가, 이어서 재정비할 때 다시 다듬습니다. 새 윤문 설정의 실행 기록은 예전 체크포인트와 혼합하지 않도록 관리됩니다.

재정비 창 보기 (v2.5)

재정비 창은 처음 열 때의 크기 그대로 끝까지 유지됩니다. 진행 중에는 진행바 아래 첫 줄에 교정 N/전체 문단 · 원문 보존 · 경과 · 남은 예상 시간, 그 아래에 지금 하는 일 · 응답 대기 N초가 나오며, 이 줄이 길어지거나 짧아져도 창이나 버튼이 움직이지 않도록 자리가 미리 잡혀 있습니다. 끝나면 진행바 자리에 "✓ 정비 완료"가 나오고 아래에 총 소요 시간 · 기준표 · 실제 변경/원문과 동일/원문 보존 문단 수 · 결과 파일 이름이 나옵니다. 긴 파일 이름은 가운데를 줄여 보여 주며, 결과·검토 기록 파일의 전체 경로는 그 글 위에 마우스를 올리면 나옵니다. 정책 차단(거부)은 모델의 답이 도착해야 알 수 있으므로, 응답 대기 시간이 길어도 거부인지 아닌지는 답이 온 뒤에 기록됩니다.

장편의 처리 속도는 모델 크기와 문맥 길이, GPU/RAM 여유에 따라 달라집니다. 재정비 입력은 10MB 미만의 TXT 파일만 지원하므로 큰 파일은 제한에 걸릴 수 있으며, 그 경우 원본을 보관하고 분할해서 작업하세요. 원문 파일은 따로 보관하고 결과 검토 기록에서 보존 사유를 확인합니다.

7. 번역 안 된 부분 다시 번역하기

엔진이 거부하거나 서버가 막은 문단은 원문 그대로 결과 파일에 남습니다(부분 완료, .ko.partial.txt). 이런 부분은 그 부분만 다시 번역할 수 있습니다. 이미 번역된 부분은 다시 요청하지 않아 추가 요금이 들지 않습니다.

자동으로 묻고, 자동으로 다시
  • 파일 하나 · 붙여넣은 글 — 번역이 끝났는데 미번역 부분이 있으면 묻지 않고 작업 기록에 남은 부분을 적은 뒤 이어서 자동으로 남은 부분만 다시 번역합니다(최대 2회, 남은 수가 줄지 않으면 같은 엔진이 계속 막는 것이라 멈춤). 본문 번역과 재시도가 한 기록으로 이어지고, 걸린 시간도 합쳐서 마지막에 한 번 나옵니다. 기록: ↻ 본문 번역 끝 · 미번역 … · 남은 부분만 이어서 자동으로 다시 번역 (1/2회) → 작업 끝 · 걸린 시간 … (본문 번역 + 미번역 재시도 1회 포함). 그래도 남으면 "번역 완료 · 일부 남음" 창에 남은 부분과 이유가 나오고, 언제든 번역 시작 / 계속으로 다시 시도할 수 있습니다. API 설정에서 다른 엔진을 켜 두면 더 잘 됩니다.
  • 폴더 번역 — 파일 하나와 똑같이 파일마다 미번역 부분을 묻지 않고 자동으로 다시 번역한 뒤 다음 파일로 넘어갑니다(최대 2회, 남은 수가 줄지 않으면 멈춤). 기록: 파일이름 · ↻ 본문 번역 끝 · 미번역 … · 남은 부분만 이어서 자동으로 다시 번역 (1/2회). 그래도 남은 파일이 있으면 마지막 창이 "폴더 번역 완료 · 일부 남음"으로 바뀌어 그 파일들을 알려 주고, 미완료 목록 탭에는 파일마다 ── 파일 이름 ── 아래에 남은 위치가 쌓입니다. 번역_요약.txt 맨 아래 남은 미번역 상세에도 파일별 청크 번호와 원문으로 남은 문단 번호(P000123)가 적힙니다. 같은 폴더로 번역 시작 / 계속을 누르면 남은 부분만 다시 시도합니다.

7-1. 무엇이 남았는지 확인

  • 작업이 끝나면 완료 창과 상태 / 오류 기록에 "원문으로 남은 문단 N개", "한자·가나가 남은 문단 N개"가 나옵니다.
  • 미완료 목록에 위치(문단 번호)와 이유가 나옵니다. 결과 파일은 이름.ko.partial.txt 하나만 생기며, 원문으로 남은 부분도 그 안에 빠짐없이 들어 있습니다(별도 목록 파일은 만들지 않습니다).

7-2. 다시 번역하는 방법

상황이렇게
잠깐의 오류·한도 때문에 남음묻는 창에서 재시도, 또는 같은 파일을 열고 번역 시작 / 계속. 같은 엔진으로 그 부분만 다시 보냅니다.
엔진이 거부·차단해서 남음API 설정에서 다른 엔진(OpenAI나 로컬 LLM)을 켜거나 맨 위로 올린 뒤 같은 파일로 번역 시작 / 계속. 같은 엔진은 대개 같은 문단을 또 막습니다.
번역은 됐는데 한자·가나가 몇 글자 섞임같은 파일로 번역 시작 / 계속. 그 글자만 고치는 요청을 보내고, 짧은 문단은 새로 번역합니다. 더 큰 모델을 쓰면 줄어듭니다.
문단 안에서 몇 문장만 원문으로 남음같은 파일로 번역 시작 / 계속. 남은 문장들만 모아 한 번에 보내고, 이미 번역된 문장은 그대로 둡니다.
설정을 바꿔서 전체를 새로처음부터 다시 (요금이 다시 듭니다)

재시도는 처음 번역과 같은 순서를 되풀이하지 않고, 지난번 막힌 이유에 맞춰 더 세밀하게(앞 문맥 없이, 문단 단위로) 요청합니다(부록 A-4).

안심 · 다시 시도하다 실패해도 이전 번역은 지워지지 않습니다. 결과 파일을 덮어쓰기 전에는 .before_날짜시간.bak 백업도 남깁니다(직접 고친 내용 보호).

8. 멈추기 · 이어서 번역

  • 일시정지 — 진행 중인 요청 하나를 마무리해 저장한 뒤 멈춥니다. 다시 진행으로 그 자리에서 계속합니다. 폴더 작업이면 다음 파일도 멈춘 상태로 기다립니다.
  • 번역 중지 — 지금까지 한 것을 저장하고 끝냅니다. 결과는 .ko.partial.txt로 저장됩니다. v2.5부터 로컬 LLM(Ollama)이 쓰고 있던 답도 그 자리에서 끊어, 그래픽카드가 아무도 기다리지 않는 청크를 끝까지 만들지 않습니다. 그래서 중지 직후 새 번역이나 재정비를 시작해도 이전 요청 뒤에 줄 서서 기다리지 않습니다. 끊긴 청크는 저장되지 않은 채 남아 있다가, 이어서 번역할 때 처음부터 다시 요청됩니다(이미 완료된 청크는 그대로).
  • 번역 시작 / 계속 — 같은 파일을 다시 열고 누르면 번역된 부분은 그대로 쓰고 남은 부분만 번역합니다. 프로그램을 껐다 켜도, PC가 꺼졌어도 됩니다.
  • 처음부터 다시 — 저장된 번역을 쓰지 않고 처음부터 새로 번역합니다(요금이 다시 듭니다).
중지와 일시정지의 차이 (로컬 LLM)

일시정지는 지금 받고 있는 답을 끝까지 받아 저장한 뒤 멈추므로, 그 청크의 결과를 잃지 않습니다. 번역 중지는 바로 끝내는 버튼이라 받고 있던 답은 버리고 Ollama의 생성도 즉시 멈춥니다. 긴 청크를 거의 다 받았을 때 끝내고 싶다면 일시정지 후 중지를 누르면 그 청크까지 저장됩니다. Ollama 기본 연결이 아닌 LM Studio 같은 OpenAI 호환 주소를 쓰면 서버 쪽 생성은 그 요청이 끝날 때까지 이어질 수 있습니다(앱은 바로 멈추고 늦게 온 답은 쓰지 않습니다). 한국어 소설 재정비의 "안전 중지"는 지금 다듬고 있는 묶음의 답을 받아 저장한 뒤 멈추는 방식이라, 답이 오기까지 조금 기다릴 수 있습니다.

10. 비용 · 한도 · 속도

비용

  • 번역이 끝나면 상태 / 오류 기록에 엔진별 요청 수, 토큰 수, 추정 비용(그중 재시도·확인 요청에 든 비용)이 나옵니다. Gemini 프로젝트의 등급을 지정하면 프로젝트별 무료($0)/유료(모델 가격으로 추정) 사용량을 구분합니다. 등급 미지정 프로젝트는 청구 등급을 확인할 수 없으므로, 기존 설정처럼 유료 가격으로 추정하거나 혼합 사용 시 청구액 미확정으로 안내합니다. 실제 요금은 Google AI Studio의 결제 화면 기준입니다.
  • 기본 Gemini 3.1 Flash Lite는 100만 토큰당 입력 $0.25 / 출력 $1.50입니다. 중국어 30만 자 정도 장편 한 권이 대략 1~2달러(막힌 부분 재시도가 많으면 조금 더)입니다.
  • 막힌 문단 하나에 쓰는 유료 요청 수에 상한(청크당 16회)이 있어, 같은 문단에 요금이 계속 나가지 않습니다.

한도

  • Gemini 한도는 프로젝트 단위입니다. 한도에 걸리면 다른 프로젝트 그룹의 키 → 다음 엔진 → 기다렸다 자동으로 이어 번역 순서로 처리합니다(3-3).
  • 무료 키는 분당·하루 한도가 낮습니다. 정확한 숫자는 Google AI Studio에서 확인하세요.

속도

  • 원문 길이보다 막히는 문단이 얼마나 많은가가 시간을 크게 좌우합니다. 막힘이 많은 글은 복구에 요청이 여러 번 들어 오래 걸립니다.
  • 하단 API 상태 줄의 "속도 조절 대기 6초 · 현재 10.0회/분"은 고장이 아니라 요청 간격을 지키는 중이라는 뜻입니다.
  • 자세한 원리와 수치는 부록 B에 있습니다.

11. 로컬 LLM (Ollama)

보조 엔진의 지연 로딩과 자동 해제 · 로컬 LLM을 두 번째 엔진으로 선택해도, 실제로 로컬 번역이 필요하기 전에는 Ollama 모델을 미리 로드하지 않습니다. 처음 호출했을 때 모델을 불러오며, 마지막 Ollama 요청 뒤 유휴 상태가 5분 지속되면 Ollama의 keep_alive 설정에 따라 모델이 자동 해제됩니다. 같은 5분 안에 다시 호출하면 모델을 재사용할 수 있습니다. 모델 목록 조회나 API 설정창을 여는 것만으로 이 설정의 사전 예열은 하지 않습니다. LM Studio 같은 다른 호환 서버에는 이 Ollama 전용 설정을 보내지 않습니다. 별도 프로그램에서 같은 모델을 사용하거나 Ollama 서버 자체 설정이 다르면 메모리 해제 시점이 달라질 수 있습니다.

내 PC의 그래픽카드로 돌리는 번역 엔진입니다. 요금과 서버 차단이 없지만 클라우드 모델보다 느리고, 품질은 모델에 따라 다릅니다.

  1. Ollama를 설치하고 모델을 받아 둡니다(명령 프롬프트에서 ollama pull 모델이름).
  2. API 설정 → 로컬 LLM 탭을 열면 Ollama에 등록된 모델 목록을 자동으로 가져옵니다. 모델 이름 목록에서 고르세요(직접 입력도 됩니다). 목록이 비어 있으면 Ollama가 켜져 있는지 확인하고 목록 불러오기를 누르세요.
  3. 로컬 LLM 연결 테스트로 확인합니다. 결과에 생성 속도(토큰/초)가 나옵니다.
  4. 번역 엔진 순서에서 로컬 LLM에 체크합니다. LM Studio도 LM Studio 버튼으로 주소를 넣어 쓸 수 있습니다.

구조화 출력 (자동)Ollama에 "보낸 문단 ID가 모두 들어간 형식으로만 답하라"고 지정합니다. 모델이 문단을 빠뜨리거나 합칠 수 없어 다시 요청이 크게 줄어듭니다. 서버가 지원하지 않으면 자동으로 끄고 예전 방식으로 받습니다. 설정: config\app.json → local_llm.structured_output
샘플링 (자동)Gemma 모델의 번역·재정비 본문은 Google 권장값(temperature 1.0, top_p 0.95, top_k 64)을 씁니다. 다른 모델과 용어·말투 분석, 재정비 분석·연속성 확인은 안정적인 0.2를 씁니다. 앱이 요청마다 보내므로 Modelfile의 값보다 우선합니다. 설정: local_llm.sampling (recommended / 모든 경우 0.2는 fixed)
한 번 요청의 문단 수 (기본 12)짧은 줄이 많은 소설은 한 청크에 문단이 50개 이상이라, 로컬 LLM에는 12문단씩 나눠 보냅니다. 청크 구성·이어 번역·번역 기억은 바뀌지 않습니다. 설정: local_llm.max_paragraphs_per_request (0이면 제한 없음)
느리거나 "응답 시간 초과"가 날 때 · 명령 프롬프트에서 ollama ps를 실행해 보세요. PROCESSOR 칸이 100% GPU가 아니면(예: 30%/70% CPU/GPU) 모델이 그래픽카드 메모리에 다 들어가지 않은 것입니다. 더 작은 모델이나 낮은 양자화(Q4)를 쓰거나, 그래픽카드를 쓰는 다른 프로그램을 닫으세요. 16GB 그래픽카드라면 14B 이하 Q4~Q6 모델이 알맞습니다.

작은 모델에서 자주 생기는 문제(반복, 남은 한자, 영어 혼잣말 섞임)는 프로그램이 자동으로 걸러 내고 다시 요청합니다. 자세한 장치는 부록 F에 있습니다.

11-1. 처음부터 설치하기 — Windows Ollama + Gemma 4 12B Q8 GGUF

처음 사용하는 분은 아래 1~9단계를 위에서 아래로 따라 하세요. Ollama는 선택 사항입니다. Gemini 또는 OpenAI API만으로 먼저 번역해도 되지만, 일부 콘텐츠는 온라인 AI 서비스의 정책에 따라 번역 요청이 거부될 수 있습니다. 그럴 때를 대비해 로컬 LLM을 추가로 설치해 둘 수 있습니다. 모델은 PC 안에서 실행되며, 충분한 RAM·GPU 메모리와 디스크 공간이 필요합니다.

  1. 1단계 — Windows용 Ollama 다운로드. 공식 Ollama Windows 다운로드 페이지를 열고 Windows 설치 파일을 내려받으세요. 공식 사이트가 아닌 임의의 다운로드 사이트는 이용하지 마세요.
  2. 2단계 — Ollama 설치 및 실행 확인. 받은 설치 파일을 실행하고 안내에 따라 설치하세요. 설치를 마친 다음 Windows 시작 메뉴에서 Ollama를 실행합니다. Windows 키 → cmd 입력 → 명령 프롬프트를 열고 다음 명령을 입력하세요.
ollama --version

버전이 나오면 설치를 확인한 것입니다. 'ollama 명령을 찾을 수 없습니다'가 나오면 명령 프롬프트를 닫고 다시 열거나 Windows에 다시 로그인한 뒤 확인하세요. 설치 후 서버 연결이 되지 않으면 Ollama가 실제로 실행 중인지 확인하세요.

  1. 3단계 — 모델 파일 다운로드. Hugging Face의 GGUF 파일 목록을 열고 gemma-4-12B-it-uncensored-heretic-Q8_0.gguf를 선택해 파일 페이지의 Download로 내려받으세요. 약 12.7GB의 큰 파일이므로 충분한 여유 공간을 준비하고 다운로드가 완료됐는지 확인하세요. 이 모델은 커뮤니티 수정판이므로 모델 카드와 이용 조건도 확인하세요.
  2. 4단계 — 모델용 폴더 만들기. 탐색기에서 C:\AI\Models\Gemma12B 폴더를 새로 만들고 다운로드한 GGUF 파일을 그 폴더로 옮기세요. 경로는 예시이므로 다른 드라이브(예: D:\LLM\Gemma12B)를 사용해도 됩니다. 파일명은 변경하지 마세요.
  3. 5단계 — Modelfile 만들기. Windows 메모장을 실행하고 아래 7줄을 그대로 복사하여 붙여 넣으세요.
FROM ./gemma-4-12B-it-uncensored-heretic-Q8_0.gguf
RENDERER gemma4-large
PARSER gemma4
PARAMETER num_ctx 16384
PARAMETER temperature 1.0
PARAMETER top_p 0.95
PARAMETER top_k 64

RENDERER gemma4-large와 PARSER gemma4는 Gemma 4 12B·26B에 맞는 대화 형식을 Ollama에 직접 알려 줍니다. 이 줄이 없으면 Ollama가 모델 이름으로 형식을 고르는데, 12B는 이름에 소문자 12b가 없으면 작은 모델용 형식이 쓰일 수 있습니다. 샘플링 값은 Google 권장값이며, 번역 앱은 요청마다 알맞은 값을 따로 보내므로 앱에서는 이 값보다 앱 설정이 우선합니다. 이미 등록한 모델도 이 두 줄을 넣은 Modelfile로 ollama create를 다시 실행하면 그대로 갱신됩니다.

메모장 → 파일 → 다른 이름으로 저장을 클릭하세요. 저장 위치를 C:\AI\Models\Gemma12B로 지정하고, 파일 이름에 Modelfile-gemma-4-12B-Q8, 파일 형식에 모든 파일 (*.*), 인코딩에 UTF-8을 선택한 다음 저장합니다. 파일 이름 끝에 .txt가 붙으면 안 됩니다. 탐색기의 보기 → 표시 → 파일 확장명을 켜서 확인하세요. FROM ./...은 Modelfile과 GGUF가 같은 폴더에 있다는 뜻입니다.

6단계로 가기 전 폴더 확인. C:\AI\Models\Gemma12B 안에 아래 두 파일이 나란히 있어야 합니다.
gemma-4-12B-it-uncensored-heretic-Q8_0.gguf
Modelfile-gemma-4-12B-Q8
첫 번째는 다운로드한 모델 파일, 두 번째는 메모장으로 직접 만든 설정 파일입니다.
  1. 6단계 — 모델 등록. Windows 명령 프롬프트(CMD)를 실행하고 아래 두 줄을 한 줄씩 입력한 뒤 Enter를 누르세요. 첫 번째 줄은 모델 파일이 있는 폴더로 이동하고, 두 번째 줄은 GGUF를 Ollama에 등록합니다.
cd /d C:\AI\Models\Gemma12B
ollama create gemma-4-12B-it-uncensored-heretic-Q8 -f Modelfile-gemma-4-12B-Q8

중요: ollama create의 첫 번째 모델명 gemma-4-12B-it-uncensored-heretic-Q8은 Ollama에 등록할 이름입니다. -f Modelfile-gemma-4-12B-Q8은 5단계에서 만든 설정 파일 이름이며, FROM 안의 .gguf는 실제 다운로드한 모델 파일 이름입니다. 세 이름은 역할이 다르므로 예제를 그대로 사용하세요. 이 명령은 GGUF를 다시 다운로드하지 않고 로컬 파일을 등록합니다. 완료될 때까지 명령 프롬프트를 닫지 마세요. PowerShell을 사용하는 분은 첫 줄 대신 cd C:\AI\Models\Gemma12B를 입력하세요.

  1. 7단계 — 등록 확인. 같은 명령 프롬프트에서 아래 두 명령을 순서대로 실행하고, 목록에 gemma-4-12B-it-uncensored-heretic-Q8가 나오는지 확인하세요.
ollama list
ollama show gemma-4-12B-it-uncensored-heretic-Q8
  1. 8단계 — 모델 실행 시험. 다음 명령을 입력하고 모델이 준비되면 짧은 한국어 질문을 입력해 응답하는지 확인하세요. 끝낼 때는 /bye를 입력합니다. 첫 실행은 모델을 메모리에 올리느라 시간이 걸릴 수 있습니다.
ollama run gemma-4-12B-it-uncensored-heretic-Q8
  1. 9단계 — 야문 Novel Translator에 연결. Ollama를 실행한 상태에서 앱의 API 설정 → 로컬 LLM 탭으로 이동합니다. 로컬 LLM을 사용으로 켜고, 서버 주소는 기본값 http://127.0.0.1:11434를 사용하세요. 목록 불러오기를 누른 뒤 등록된 gemma-4-12B-it-uncensored-heretic-Q8를 선택하고 로컬 LLM 연결 테스트를 실행합니다. 성공하면 설정을 저장하세요. 온라인 API 키 없이 로컬 모델만으로 번역하려면 이어지는 11-2절의 엔진 설정도 따라 하세요.
모델이 느리거나 메모리 부족일 때 · Q8_0 GGUF는 약 12.7GB이며 실제 실행에는 문맥(KV 캐시)과 작업 메모리가 추가로 필요합니다. GPU 16GB여도 컨텍스트·다른 프로그램 사용량에 따라 완전히 GPU에 올리지 못할 수 있습니다. ollama ps로 CPU/GPU 사용 비율을 확인하고, 문제가 있으면 같은 모델 저장소의 더 작은 Q4_K_M 등 다른 양자화 버전을 별도 등록하세요. num_ctx 16384는 예시값이므로 PC 메모리가 부족하면 낮춰 새로 등록할 수 있습니다.
문제가 생길 때 확인할 항목
  • ollama 명령을 찾지 못함: 설치 완료 후 CMD를 다시 열거나 재로그인하고 실행 상태를 확인합니다.
  • GGUF 파일을 찾지 못함: 두 파일의 위치가 같은지, FROM이 실제 GGUF 이름과 같은지 확인합니다.
  • Modelfile을 찾지 못함: Modelfile-gemma-4-12B-Q8.txt로 잘못 저장되지 않았는지 확인합니다.
  • 앱 모델 목록에 표시되지 않음: ollama list의 등록명과 앱에서 선택한 이름을 비교하고, 서버 실행 상태 및 목록 불러오기를 확인합니다.
  • 등록 설정 확인: ollama show gemma-4-12B-it-uncensored-heretic-Q8 --modelfile을 사용합니다.

재정비용 Ollama 모델 등록·교체

앞의 1~9단계를 마치고 API 설정의 용어·말투 분석과 문학적 윤문·연속성에서 각각 로컬 LLM 및 등록된 모델을 선택하세요. 모델 목록이 비면 먼저 ollama list와 Ollama 서버 실행 여부를 확인한 뒤 앱에서 목록 불러오기를 누릅니다.

11-2. API 키 없이 로컬 LLM만으로 번역하기

  1. Ollama를 실행해 두고 ollama list로 등록 모델을 확인합니다. 기본 Ollama 주소는 http://127.0.0.1:11434입니다. 앱에서 직접 로컬 서버 주소를 설정했다면 실제 사용 중인 주소를 입력하세요.
  2. 야문 Novel Translator 실행 → API 설정 → 로컬 LLM을 사용으로 켜고 목록 불러오기로 gemma-4-12B-it-uncensored-heretic-Q8를 선택하세요. 모델 이름은 등록된 이름과 일치해야 합니다. 로컬 LLM 연결 테스트를 실행합니다.
  3. 번역 엔진 순서에서 로컬 LLM만 활성화하고 Gemini·OpenAI는 번역 엔진 목록에서 제외합니다. 클라우드 API 키를 발급하거나 입력할 필요가 없습니다. 다만 인명·용어 추출과 인물 말투표 자동 생성은 별도 엔진 설정이므로, API 설정의 용어·말투 분석에서도 로컬 LLM을 선택하면 클라우드 키 없이 진행하기 쉽습니다.
  4. 중국어·일본어·영어 TXT를 열고 번역 시작 / 계속을 누릅니다. Ollama에서는 모든 문단 ID가 반드시 들어간 형식으로 답을 받으므로 문단 빠짐으로 인한 재시도는 드뭅니다. 다만 내용을 제대로 번역하지 않으면(원문 그대로, 반복 등) 앱이 검증·재시도를 진행해 속도가 늦어질 수 있습니다. 로컬 엔진 하나만 설정했다면 클라우드 보조 엔진으로 자동 복구할 수 없는 점도 기억하세요.
자주 생기는 문제
  • 모델 목록에 없음: ollama list에서 등록명 확인 → 앱의 모델 목록 새로고침. Ollama가 종료되었다면 다시 실행하세요.
  • create에서 GGUF 파일을 찾지 못함: Modelfile-gemma-4-12B-Q8의 FROM이 실제 파일명·폴더와 일치하는지 확인하고, .txt가 붙지 않았는지 점검하세요.
  • 모델이 너무 느림/메모리 부족: ollama ps에서 GPU/CPU 사용 비율을 확인하고, 메모리가 부족하면 더 작은 GGUF로 별도 이름을 등록하세요.
  • 설정을 다시 확인하고 싶음: ollama show gemma-4-12B-it-uncensored-heretic-Q8 --modelfile로 Ollama가 실제 적용한 설정을 확인하세요. 여기 나오는 내부 blob 경로를 새 Modelfile에 그대로 붙여 넣을 필요는 없습니다.
  • 기존 등록 모델을 제거할 때: ollama rm gemma-4-12B-it-uncensored-heretic-Q8는 Ollama 등록 모델을 삭제하는 명령입니다. 필요한 모델을 실수로 삭제하지 않도록 주의하세요.

12. 자주 묻는 질문

번역 시작 버튼이 눌리지 않아요

아래 준비 상태 줄을 보세요. 원문이 없거나, 쓸 수 있는 엔진이 없으면(키가 없거나 체크가 안 됨) 눌리지 않습니다.

일부 문단이 원문(중국어)으로 남았어요

엔진이 거부했거나 막힌 부분입니다. 끝날 때 묻는 창에서 재시도를 누르거나 같은 파일로 번역 시작 / 계속을 다시 누르세요. 같은 엔진이 계속 막으면 다른 엔진을 켜세요(7장).

키를 10개 넣었는데 하나만 쓰여요

정상입니다. 평소에는 맨 위 키 하나만 쓰고, 나머지는 예비입니다. 한도는 프로젝트 단위라 같은 프로젝트의 키를 돌려 써도 늘어나지 않습니다. 프로젝트 그룹 이름이 프로젝트마다 다르게(P1, P2…) 되어 있는지만 확인하세요(3-3).

분당 한도를 넘으면 키가 정지되나요?

보통은 그 요청이 거절(429)될 뿐이고 잠시 뒤 다시 됩니다. 이 프로그램은 요청을 하나씩 보내고, 거절되면 스스로 속도를 낮춥니다. 정확한 한도 숫자는 Google AI Studio에서 확인하세요.

말투가 두 사람 관계에 안 맞아요

인물 말투 탭에서 그 두 사람의 줄을 확인하세요. 줄이 없으면 말투 추가로 넣고, 틀렸으면 말투 칸에서 고르면 됩니다. 다음 요청부터 적용됩니다(6-4).

아들이 화자인데 "누나"가 아니라 "언니"로 나와요

중국어 姐는 성별 구분 없이 "손위 여자"라서, 화자의 성별을 모르면 모델이 "언니"로 기울기 쉽습니다. 인물 말투 탭에서 "나 → 엄마" 줄의 관계·메모가 "모자"로 되어 있는지 보세요. 비어 있거나 틀렸으면 "모자"라고 적으면 화자가 남자로 정해지고, 번역에 "姐는 누나" 규칙이 함께 갑니다. 확정 용어집에 ○○姐 → ○○ 언니 같은 항목이 있으면 한국어 표기만 "○○ 누나"로 고치세요(다시 번역하지 않음, 16-2).

번역할 때마다 "남은 한자·가나 정리" 기록이 자주 나와요

모델이 남긴 원문 글자를 프로그램이 잡아 그 문단만 한글로 다시 고친 기록입니다. 오류가 아닙니다. 3비트대 양자화에서 자주 생기며, VRAM에 다 들어가는 범위에서 IQ4_XS 같은 4비트 모델로 바꾸면 대개 줄어듭니다(14-2).

더 큰 모델(Q4_K_M)로 바꿨더니 두 배로 느려졌어요

모델이 그래픽카드 메모리에 다 들어가지 않아 일부가 CPU에서 돌고 있을 가능성이 큽니다. 번역 중에 ollama ps를 실행해 PROCESSOR가 100% GPU인지 확인하세요. 아니라면 같은 모델의 IQ4_XS처럼 조금 작은 파일을 쓰세요(14-3).

재정비 창에 "번역 기록 없음 · 샘플 분석"으로 나와요

그 TXT를 이 버전에서 번역한 기록이 없을 때입니다(다른 번역기 결과, 예전 버전 결과 등). 이 앱으로 번역한 책이라면 원문을 열고 번역 시작 / 계속으로 한 번 마무리하면(이미 번역된 부분은 다시 요청하지 않음) 결과와 번역 기록이 연결됩니다.

데이터 폴더의 logs 폴더를 지워도 되나요?

logs에는 분석 답 기록·형식 진단 기록·오류 보고서 같은 기록 파일만 있습니다. 번역 진행 기록(translations.db), 키, 용어집은 그 위 폴더에 있으므로 지워도 번역 기록은 사라지지 않습니다. 다만 프로그램이 켜져 있을 때 지우면 기록을 쓰던 중에 오류가 날 수 있으니 프로그램을 닫은 뒤 지우세요. 다음 실행 때 폴더는 다시 만들어집니다.

이름이 중간에 바뀌어요

확정 용어집에 그 이름을 적어 두세요. 자동 추출을 쓰면 편합니다.

중국 이름이 "쭤징"처럼 나와요

확정 용어집 탭 맨 위 중국 인명 표기를 한국 한자음으로 고르고, 다시 추출할지 물으면 새 방식으로 다시 추출을 누르세요(6-2).

이름 표기를 바꿨는데 "하늘색"의 하늘은 그대로예요

정상입니다. v2.5부터 이름 바로 뒤에 조사·어미·호칭이 아닌 글자가 붙은 곳은 다른 낱말의 일부로 보고 바꾸지 않습니다(6-8). 작업 기록의 "다른 낱말의 일부로 보이는 N곳은 그대로 둠"이 그 수입니다. 정말 이름인데 남았다면(예: 이름 뒤에 흔치 않은 호칭을 붙여 쓴 경우) 결과 파일에서 직접 고치거나, 확정 용어집을 고친 상태로 처음부터 다시 번역하세요.

번역을 중지했는데 그래픽카드가 한동안 계속 돌았어요

v2.41까지는 번역 중지를 눌러도 Ollama가 쓰던 청크를 끝까지 만들었습니다. v2.5부터는 중지하는 순간 Ollama와의 연결을 닫아 생성도 함께 멈춥니다. 그래도 계속 돈다면 LM Studio 같은 OpenAI 호환 주소를 쓰는 경우(서버가 요청을 끝까지 처리)이거나, 한국어 소설 재정비의 안전 중지처럼 지금 묶음의 답을 기다리는 경우입니다. ollama ps로 모델이 아직 작업 중인지 볼 수 있으며, 모델은 쓰지 않으면 5분 뒤 메모리에서 내려갑니다.

재정비 창의 결과 경로가 잘려 보여요

창 크기가 흔들리지 않도록 긴 파일 이름은 가운데를 줄여 보여 줍니다. 결과·검토 기록의 전체 경로는 그 글 위에 마우스를 올리면 나오고, 파일은 출력 폴더(지정하지 않았다면 원본 TXT 옆)에 있습니다.

글자가 깨져 보여요

TXT 인코딩을 직접 골라 보세요(중국어 간체 GB18030, 번체 Big5, 일본어 CP932 · EUC-JP). PDF에서 꺼낸 글이 깨져 보이면 글꼴에 글자 정보가 없는 PDF입니다. 문자 인식(OCR)으로 만든 TXT를 쓰세요.

PDF를 열었더니 "문자 인식(OCR)이 필요한 PDF"라고 나와요

종이를 스캔해 만든 그림 PDF라 꺼낼 글자가 없습니다. 이 프로그램은 문자 인식을 하지 않습니다. OCR 프로그램으로 글자가 들어간 PDF나 TXT를 만든 뒤 여세요(4-4).

EPUB을 열었더니 "복제 방지(DRM)"라고 나와요

서점에서 산 전자책은 대부분 복제 방지가 걸려 있어 그 서점의 앱에서만 읽을 수 있습니다. 이 프로그램은 복제 방지를 풀지 않습니다.

PDF 번역문의 문단이 이상하게 나뉘어요

PDF에는 문단 정보가 없어 줄 길이 · 들여쓰기 · 문장부호로 문단을 다시 잇습니다. 원문 창에서 고친 뒤 번역 시작 / 계속을 누르면 고친 내용대로 번역합니다.

번역이 갈수록 느려져요

막힌 문단을 나눠 다시 요청하느라 시간이 더 듭니다. 하단 API 상태에 "속도 조절 대기"가 보이면 요청 간격을 지키는 중입니다. 작업 끝 요약에 걸린 시간과 그 원인이 나옵니다(부록 B).

도중에 PC가 꺼졌어요

그대로 다시 열고 번역 시작 / 계속을 누르면 이어집니다.

13. 저장 위치 · 보안

  • 번역 진행 기록, 붙여넣은 글의 임시 파일, 내 번역 지침: %LOCALAPPDATA%\NovelTranslator (보통 C:\Users\사용자\AppData\Local\NovelTranslator)
  • 로컬 LLM 형식 진단 기록: 같은 폴더의 logs\format_diagnostics.log (문단 ID 문제가 생겼을 때만 만들어짐, 본문과 키는 기록하지 않음)
  • API 키는 Windows 보안 저장(DPAPI)으로 암호화해 이 PC의 내 계정에서만 읽을 수 있게 저장합니다. 로그와 결과 파일에는 키를 남기지 않습니다.
  • 설정 파일: 프로그램 폴더의 config, 언어 규칙: profiles
  • 새 버전으로 바꿀 때는 새 폴더에 압축을 풀어 쓰면 됩니다. 키와 진행 기록은 위 위치에 남아 있어 그대로 이어집니다.
알아 두면 좋은 것로컬 LLM 고르기와 설정, 좋은 번역을 만드는 순서, 용어집·말투표·재정비를 잘 쓰는 요령. 읽어 두면 "아, 그래서 그랬구나" 싶은 것들.

14. 로컬 LLM 고르기와 설정

이 프로그램은 로컬 LLM이 주 엔진입니다. 같은 Gemma 4 모델이라도 크기·양자화·설정에 따라 품질과 속도가 크게 달라집니다. 이 장은 "내 PC에서 어떤 파일을 받아 어떻게 설정하면 좋은가"를 한 번에 정리합니다.

14-1. 모델 이름 읽는 법

Hugging Face에서 받는 GGUF 파일 이름에는 필요한 정보가 다 들어 있습니다. 예를 들어 gemma-4-26B-A4B-it-uncensored-heretic.i1-IQ4_XS.gguf는 이렇게 읽습니다.

부분뜻번역에 미치는 영향
gemma-4모델 계열(Google Gemma 4)이 프로그램은 Gemma 4에 맞춘 대화 형식·샘플링을 자동으로 씁니다.
26B전체 매개변수 260억 개클수록 문장력·문맥 파악이 좋고, 파일과 메모리도 커집니다.
A4BActive 4B — 한 글자를 만들 때 실제로 쓰는 매개변수는 약 40억 개(MoE 구조)26B의 지식을 쓰면서 속도는 4B 모델에 가깝습니다. 그래서 26B A4B가 12B보다 빠른 경우가 많습니다.
itInstruction-tuned — 지시를 따르도록 다듬은 모델번역에는 반드시 it 모델을 쓰세요.
uncensored · abliterated · heretic거부 성향을 줄인(거부 해제) 모델. 만든 사람마다 방식과 이름이 다릅니다.성인 장면이 있는 소설을 끝까지 번역하려면 거의 필수입니다. 방식이 달라 같은 크기라도 거부율·문체가 조금씩 다릅니다.
i1imatrix(중요도 자료)를 써서 만든 양자화같은 크기에서 품질이 조금 더 좋습니다.
IQ4_XS, Q4_K_M …양자화 방식과 크기(다음 절)VRAM에 다 들어가느냐가 여기서 정해집니다.

14-2. 양자화: Q와 IQ, 그리고 M · S · L

양자화는 모델을 작게 줄이는 방법입니다. 숫자(비트)가 클수록 원래 모델에 가깝고 파일도 큽니다.

  • Q 계열(K-quant: Q3_K_M, Q4_K_M, Q5_K_M …) — 오래 쓰여 온 표준 방식. 계산이 단순해서 GPU든 CPU든 빠릅니다. 4비트 이상에서는 품질이 충분하지만 3비트 이하로 내려가면 손실이 커집니다.
  • IQ 계열(i-quant: IQ3_M, IQ4_XS …) — 여러 값을 묶어 미리 정한 패턴표에서 고르는 새 방식. 같은 크기면 Q보다 품질이 좋고, 특히 3~4비트에서 차이가 납니다. 대신 CPU에서 계산하면 Q보다 느립니다.
  • 뒤의 S · M · L · XS — 같은 비트 안에서 중요한 층을 얼마나 더 높은 비트로 남기느냐에 따른 크기 단계(Small · Medium · Large · eXtra Small). 업로더가 따로 만든 _P 같은 이름은 표준이 아니니 모델 설명을 확인하세요.
고르는 원칙 하나

모델이 그래픽카드 메모리(VRAM)에 다 들어가면 IQ, 일부가 CPU로 넘치면 Q. VRAM에 다 들어가는 IQ4_XS는 같은 크기의 Q3_K_M보다 품질이 좋고 속도 손해도 없습니다. 반대로 VRAM을 넘쳐 일부가 CPU에서 돌면 IQ는 Q보다 더 느려집니다.

Gemma 4 26B A4B 거부 해제 모델의 대략적인 파일 크기(업로더마다 조금씩 다름):

양자화대략 크기16GB 그래픽카드에서
IQ3_M약 12.4GB넉넉히 들어감. 품질은 Q3_K_M과 비슷하거나 약간 나음
Q3_K_M약 13.3GB들어감. 가끔 한자가 남는 실수가 늘 수 있음
IQ4_XS약 13.9~14.2GB컨텍스트를 적당히 잡으면 대개 다 들어감. 16GB에서 가장 균형 좋은 선택
Q4_K_M약 16.9GB일부가 CPU로 넘쳐 속도가 절반 가까이로 떨어지기 쉬움
Q5_K_M 이상19GB 이상24GB 이상 그래픽카드용

12B 모델은 26B A4B보다 파일이 작아도 한 글자를 만들 때 120억 개를 다 쓰므로 오히려 느릴 수 있습니다. 12B는 메모리가 부족한 PC의 대안입니다.

14-3. VRAM에 다 들어갔는지 확인하기 — ollama ps

번역을 돌려 둔 채 명령 프롬프트에서 ollama ps를 실행하세요.

NAME SIZE PROCESSOR CONTEXT hauhau-gemma4-26B_IQ4_XS 15 GB 100% GPU 16384
  • PROCESSOR가 100% GPU — 모델이 그래픽카드에 다 들어갔습니다. 가장 빠른 상태입니다.
  • 30%/70% CPU/GPU처럼 나오면 일부가 CPU로 넘친 것입니다. 더 작은 양자화(예: Q4_K_M → IQ4_XS)를 쓰거나 컨텍스트를 줄이세요.
  • SIZE는 모델 파일 + 컨텍스트(KV 캐시) + 작업 메모리입니다. 그래서 파일보다 1~2GB 큽니다.
다른 프로그램도 VRAM을 씁니다

웹 브라우저(특히 영상), 게임, 이미지 생성 프로그램이 켜져 있으면 그만큼 모델이 쓸 자리가 줄어듭니다. 번역이 갑자기 느려졌다면 다른 프로그램부터 닫아 보세요.

14-4. 컨텍스트 길이 — 얼마로 할까

컨텍스트는 "모델이 한 번에 볼 수 있는 글자 양"입니다. 한 번의 번역 요청에는 지시문 + 확정 용어집 + 인물 말투표 + 작품 메모 + 앞 문맥 + 원문 청크 + 답이 모두 들어가야 합니다.

상황한 요청에 필요한 양(대략)
번역 방식 "속도 우선"약 12,000토큰
"균형 (권장)"약 13,500~14,500토큰
"품질 우선"약 16,000~17,000토큰
한국어 소설 재정비약 8,000~13,000토큰
  • 권장값 16,384 — "균형 (권장)"과 재정비가 여유 있게 들어갑니다. API 설정 → 로컬 LLM의 컨텍스트 길이에서 정합니다.
  • 작게 잡아도 지시문이 잘리지는 않습니다. 필요한 양보다 작으면 프로그램이 자동으로 늘려 보냅니다(최대 32,768). 다만 한 번 늘린 크기는 그 실행 동안 유지합니다. Ollama는 컨텍스트 크기가 바뀔 때마다 모델을 다시 불러오기 때문입니다.
  • 그래서 12,288처럼 낮춰도 이득이 없습니다. 첫 요청에서 다시 늘어나 같은 크기가 되고, 모델을 한 번 더 불러오는 시간만 듭니다.
  • 너무 크게(32,768 등) 잡으면 품질은 좋아지지 않고 VRAM만 미리 차지해, 모델 일부가 CPU로 밀려 느려질 수 있습니다.
  • Modelfile의 PARAMETER num_ctx보다 앱이 요청마다 보내는 값이 우선합니다.

15. 좋은 번역을 만드는 작업 순서

원문 열기·언어 확인→이름 표기 방식→용어 추출 확인→말투표 확인→작품 메모→번역→남은 부분 재시도→재정비(선택)→클린리더로 읽기
  1. 원문을 열고 언어·인코딩을 확인합니다. 원문 창의 글자가 깨져 있으면 TXT 인코딩을 직접 고르세요. 깨진 채 번역하면 결과도 엉망입니다.
  2. 중국 인명 표기 방식(한자음 / 중국어 발음)을 먼저 정합니다. 나중에 바꾸면 용어집을 다시 뽑아야 합니다.
  3. 인명·용어 자동 추출 결과를 훑어봅니다. 빨갛게 표시된 항목(일반 낱말, 한자가 남은 표기)은 지우세요. 이 단계에서 1~2분 고치면 번역 전체의 이름이 깔끔해집니다.
  4. 인물 말투표에서 주인공과 주요 인물의 줄만 확인합니다. 특히 1인칭 소설이면 "나 ↔ 엄마"의 관계 메모가 모자/모녀로 맞게 적혔는지 보세요(17-3).
  5. 작품 메모에 시점·세계관·호칭 규칙을 한두 줄 적습니다(18장).
  6. 번역 시작. 진행 중에도 용어집의 한국어 표기만 고치는 것은 자유입니다(다시 번역하지 않음).
  7. 끝나면 미완료·남은 한자 문단을 번역 시작 / 계속으로 다시 돌립니다. 그 문단만 다시 번역합니다.
  8. 필요하면 한국어 소설 재정비로 문장을 다듬고, 클린리더로 열어 읽습니다.
처음 번역 전에 정할수록 좋은 것

확정 용어집에 항목을 더하거나 지우기, 작품 메모, 번역 방식, 이름 표기 방식은 바꾸면 처음부터 다시 번역됩니다(6-8). 번역 중간에는 한국어 표기만 고치세요. 표기만 고치면 다시 번역하지 않고 저장된 번역의 이름만 바꿉니다.

장편·시리즈 요령

  • 아주 긴 소설은 권·부 단위로 나눠 폴더 번역을 하면 진행 상황을 보기 쉽습니다. 이어지는 권이면 폴더 번역의 파일 관계를 "한 작품의 연속 파일"로 두세요.
  • 속편은 공용 용어집 덕분에 앞 권의 이름 표기를 이어받습니다. 앞 권을 끝까지 번역한 뒤 다음 권을 시작하면 됩니다.
  • 같은 작가의 다른 작품이라면 공용 용어집의 이전 작품 이름이 끼어들지 않는지 첫 추출 결과를 한 번 보세요.

16-1. 넣을 것과 넣지 말 것

16-2. 호칭이 붙은 이름 — 이름만 확정합니다

중국어 姐(姐姐)는 손위 여자, 哥(哥哥)는 손위 남자를 부르는 말인데 한국어로는 말하는 사람의 성별에 따라 달라집니다.

호칭은 이름이 아니므로 자동 추출에서 아예 넣지 않습니다. 哥哥 · 姐姐 · 阿姨 · 嫂子 · 叔叔 같은 호칭, 앞에 二 · 老 · 小 · 表 같은 말이 붙은 것(二哥, 老二, 表哥), 성씨 한 글자에 붙은 것(李哥, 王姨, 老李)은 확정 용어집과 공용 용어집에 들어가지 않고, 번역할 때 문맥과 말투표에 따라 옮겨집니다. 작업 기록에 "호칭이라 넣지 않음 N개"로 남습니다. 이 판단은 정해진 목록이 아니라 규칙(친족 글자 + 앞말 + 성씨 한 글자)이라 三婶 · 王叔 · 表姐夫 · 小姑子처럼 처음 보는 호칭도 같은 방식으로 처리합니다. 말투표가 있는 책은 번역 요청에도 "호칭은 이 화자가 이 상대를 실제로 부르는 말로 쓸 것, 위 예는 보기일 뿐"이라는 원칙이 함께 갑니다. 어떤 인물을 호칭으로만 부르는 작품이라 꼭 이름처럼 고정하고 싶다면(예: 小妹 → 소매) 확정 용어집에 직접 넣으세요. 직접 넣은 항목은 자동 추출이 지우거나 바꾸지 않습니다.

확정 용어집은 "모든 자리에서 같은 표기"라서 丹丹姐 → 단단 언니를 넣으면 아들이 부르는 대사까지 "단단 언니"가 됩니다. 그래서 인명·용어 자동 추출은 이런 항목을 이름만 남겨 丹丹 → 단단으로 확정하고, 뒤의 호칭은 번역할 때 문맥으로 정하게 합니다. 작업 기록에 "호칭(姐·哥 등)을 뗀 이름만 확정 N개"로 남습니다. 공용 용어집도 이런 항목은 쌓지 않고, 예전에 쌓인 것은 새 책에 쓰지 않습니다.

이미 번역 중인 책에 "단단 언니"가 들어 있다면

항목을 지우고 새로 넣으면 처음부터 다시 번역됩니다. 이미 많이 번역했다면 한국어 표기만 "단단 누나"로 고치세요. 다시 번역하지 않고 저장된 번역의 이름만 바뀝니다. 새로 시작하는 책이라면 丹丹 → 단단만 두는 것이 가장 깔끔합니다.

추출 기준의 적정선

너무 많이 거르면 필요한 이름까지 빠지므로, 틀릴 일이 거의 없는 것만 프로그램이 확실히 빼고 나머지는 모델에게 권합니다.

  • 확실히 뺌 — 호칭 자체, 중국어 한 글자 항목(李 · 剑). 일본어는 한 글자 이름(誠 · 翼 · 薫)이 흔해 빼지 않습니다.
  • 모델에게 권함 — 내공 · 단전 · 장로 · 제자 · 검기 · 강호 · 무림 같은 장르 일반어, 표현 · 형용사 · 동사는 고르지 않기.
  • 그대로 — 인물 이름은 흔해도 모두 뽑습니다. 소림 · 무당 · 화산처럼 널리 아는 문파 · 지명도 표기가 흔들리지 않게 뽑을 수 있습니다(이름 표기를 중국어 발음으로 해 둔 경우 특히 필요).

추출이 끝나면 작업 기록에 "답에 든 항목 N개 중 M개 사용 · 걸러 냄: 이유별 개수"가 나오니, 꼭 필요한 이름이 걸러지지 않았는지 가끔 확인해 보세요.

16-3. 표기 고치기의 두 종류

  • 한국어 표기만 고치기(예: 좌경 → 쭤징, 단단 언니 → 단단 누나) — 다시 번역하지 않음. 뒤따르는 조사(은/는, 이/가…)도 맞춰 고칩니다. 이름 뒤에 다른 낱말이 붙은 곳(하늘색 · 백영화)은 이름이 아니므로 그대로 두고, 작업 기록에 그 수를 알려 줍니다(6-8).
  • 항목 추가·삭제 — 번역 내용이 달라지므로 새 작업(처음부터)으로 봅니다.

16-4. 자주 생기는 용어집 실수

  • 이름 + 동사가 붙은 항목(陈屿放 → 진서가 놓다) — 프로그램이 대부분 걸러 내지만, 남아 있으면 지우세요.
  • 같은 사람의 다른 표기(林雨 → 린위, 小雨 → 소우) — 별명은 따로 두되 한국어가 같은 사람임을 알아볼 수 있게 맞추면 읽기 편합니다.
  • 동명이인·다른 뜻(慢慢이 다른 책에서는 이름, 이 책에서는 "천천히") — 이 책에서 이름이 아니면 지우세요. 공용 용어집 항목은 분석 엔진이 이 책에서도 이름이라고 확인한 것만 들어옵니다.

② 앞 문맥 빼기엔진은 이전 장면의 한국어 문맥까지 포함해 요청 전체를 판단합니다. 앞 장면이 수위가 높으면 평범한 다음 청크까지 막히는 일이 있어, 문맥 없이 한 번 더 시도합니다.
③ 나누기한 청크(약 800자)에 막히는 문장이 하나만 있어도 청크 전체가 거부됩니다. 절반씩 나누면 문제없는 문단은 번역되고, 막히는 부분만 남습니다. 서버 차단은 문단 크기까지, 거부 답은 문장 단위까지 좁히며, 아주 긴 문단은 300~600자 구간으로 나눠 처리합니다.
④ 격리막히는 문단만 따로 떼어 냅니다. 나머지 문단은 이미 번역되어 저장됩니다(부분 완료).
⑤ 다음 엔진격리된 문단만 엔진 순서대로 다음 엔진(OpenAI · 로컬 LLM 등)으로 보냅니다. 비싼 엔진에는 꼭 필요한 부분만 갑니다.
⑥ 원문 유지모든 엔진이 실패한 문단만 원문으로 남기고 위치와 이유를 기록합니다. 나중에 그 부분만 다시 번역할 수 있습니다(7장).
원문을 고치지 않습니다 · 단어를 바꾸거나 가리거나, 가짜 대화 기록을 끼워 넣는 식으로 차단을 피하지 않습니다. 그래서 어떤 엔진이 정책상 끝까지 막는 문단은 다른 엔진이 있어야 번역됩니다. 엔진을 하나만 켜면 그런 문단은 원문으로 남습니다.

A-4. 다시 시도할 때는 더 세밀하게

재시도(같은 파일로 다시 실행, "재시도" 버튼, 폴더의 자동 재시도)에서는 지난번 어떻게 막혔는지 기억해 두었다가, 처음과 같은 순서를 되풀이하지 않습니다.

지난번 실패 이유재시도 방법

A-5. 범위 제외 재확인

모델이 문단에 "범위 제외"(미성년자 관련 성적 내용) 표시를 하면, 다음 엔진이 그 문단을 한 번 더 확인합니다. 일반 성인 장면을 잘못 제외한 경우에는 다음 엔진이 번역합니다. 한 모델의 과잉 판단 때문에 정상 문단이 빠지는 것을 막기 위해서입니다.

A-6. 남은 한자·가나 정리

번역은 됐는데 한자·가나가 몇 글자 섞인 문단(작은 모델에서 흔함)은 엔진 순서대로 "남은 글자만 한글로 고쳐 달라"는 짧은 요청을 보냅니다. 그래도 남으면 작업 끝에 개수를 알려 주고, 같은 파일로 다시 실행할 때 고칩니다. 확정 용어집에서 한자로 두기로 한 표기는 남은 글자로 보지 않습니다.

실측 예 · 거부가 많이 나도록 일부러 고른 400KB 중국어 성인 소설: 67청크 중 31청크가 Gemini에서 막혔지만, 위 사다리를 거쳐 원문으로 남은 것은 1문단이었습니다(로컬 LLM이 막힌 문단 7개를 대신 번역). Gemini 요청 156회, 추정 비용 약 $0.45.

B. 속도 — 무엇이 시간을 쓰는가

B-1. 시간 공식

걸리는 시간 ≈ 요청 수 × (응답 시간 + 요청 간격 대기)

  • 요청 수 = 청크 수 + 복구에 쓴 요청. 막힌 청크 하나는 사다리를 내려가며 요청을 3~10회 씁니다. 그래서 원문 길이보다 막히는 구간이 얼마나 많은가가 시간을 더 크게 좌우합니다.
  • 응답 시간 = 모델이 한 청크를 번역해 돌려주는 시간. 클라우드 모델은 보통 몇 초에서 십여 초, 로컬 모델은 그래픽카드에 따라 더 깁니다.
  • 요청 간격 대기 = 분당 한도를 넘지 않게 쉬는 시간(B-3).

위 400KB 실측에서는 걸린 시간의 약 81%가 막힌 31청크의 복구에 쓰였습니다.

막힌 31청크 복구 81%
정상 19%

400KB 중국어 성인 소설(거부가 많은 극단적 예). 평범한 소설은 복구가 거의 없어 훨씬 빠릅니다.

B-2. 요청을 하나씩 보내는 이유

이 프로그램은 요청을 한 번에 하나씩, 순서대로 보냅니다. 앞 청크의 한국어 번역을 다음 청크의 문맥으로 넘겨야 말투·호칭·장면이 이어지기 때문입니다. 여러 요청을 동시에 보내는 일괄 번역 도구는 더 빠르지만, 청크끼리 문맥을 모른 채 번역되고 분당 한도에 훨씬 쉽게 걸립니다.

그래서 실제 요청 속도는 대개 응답 시간이 정합니다. 응답에 5초가 걸리면 간격을 아무리 줄여도 1분에 12번을 넘지 못합니다. 무료 키의 분당 한도에 실제로 닿는 일이 드문 이유입니다.

B-3. 요청 간격 자동 조절

한도를 넘기면 오류(429)와 함께 수십 초씩 기다려야 해서 오히려 느려집니다. 그래서 안전한 속도로 시작해 성공이 이어지면 조금씩 올리고, 한도에 닿으면 내립니다.

C. 키 · 한도 · 엔진 전환

C-1. 키를 고르는 규칙

  1. 사용 가능한 키 중 목록에서 가장 위의 키를 씁니다. 돌아가며 쓰지 않습니다(예비 키를 이유 없이 소모하지 않기 위해).
  2. 키가 무효(AUTH)·차단(KEY_BLOCKED)되면 그 키를 끄고 다음 키로 넘어갑니다. 기록: API 키 … · AUTH · 비활성 처리
  3. 분당 한도(RATE_LIMIT)·하루 한도(QUOTA)는 프로젝트 그룹 전체를 쉬게 합니다. Google 공식 문서도 "한도는 API 키가 아니라 프로젝트 단위로 적용된다"고 밝히고 있어, 같은 그룹의 다른 키로 바꾸는 것은 의미가 없기 때문입니다.
  4. 쉬고 있지 않은 다른 그룹의 키가 있으면 바로 그 키로 이어 갑니다.

C-2. 하루 한도와 엔진 전환

하루 한도 소진→다른 프로젝트 그룹→다음 엔진으로 남은 청크 계속→10청크마다 Gemini 복귀 확인
  • Gemini가 한도 소진이나 장애로 계속 실패하면, 그 파일의 남은 청크는 다음 엔진이 이어 번역합니다. 기록: ⚠ Gemini 사용 불가 (…) → 이 파일의 남은 청크는 OpenAI로 …
  • 10청크마다 Gemini가 돌아왔는지 확인해, 돌아왔으면 다시 Gemini로 번역합니다. 기록: ↩ Gemini 복귀
  • 다음 엔진도 없으면 일시정지하고, 폴더 번역이면 기다렸다가 자동으로 이어 갑니다.

E. 품질 장치

  • 언어별 번역 규칙: 중국어·일본어·영어마다 따로 다듬은 규칙(profiles 폴더)을 씁니다. 대사의 말투, 의성어·의태어, 호칭(さん · 先輩 · 哥 · 姐), 존댓말·반말, 문장부호를 언어별로 다룹니다.
  • 자동 언어팩: 언어별 호칭·관계·장르 용어 목록(중국어 약 190개, 일본어 약 140개, 영어 약 145개 — 시아버지·장인·형수·올케·사숙·폐하·마마 같은 가족·사돈·무협·궁중 호칭 포함). 그 덩어리에 실제로 나온 단어만 "참고 힌트"로 보내고, 公公(시아버지/환관)처럼 뜻이 갈리는 말은 판별 기준을 함께 줍니다. 확정 용어가 항상 우선합니다.
  • 인물 말투표: 대사 표본에서 관계가 분명한 쌍만 뽑고, 인물 이름이 용어집에 없거나 말투가 정해진 6가지가 아니면 버립니다. 매 요청에 "이 두 사람 사이는 이 말투" 규칙으로 붙어, 덩어리마다 말투를 새로 짐작하지 않게 합니다. 작업 정체성(이어 번역 기준)에는 넣지 않아, 고쳐도 다시 번역되지 않습니다.
  • 요청에 함께 붙는 내용: 언어별 규칙, 확정 용어집, 이름 표기 방식, 인물 말투표, 작품 메모, 내 번역 지침, 앞 문맥. 내 번역 지침이 고정 규칙(빠짐없이 · 같은 문단 번호 · 한글 출력 · 확정 용어집 · 범위 제외)과 부딪치면 고정 규칙을 따르도록 함께 지시합니다.
  • 확정 용어집 우선: 용어집에 적은 표기는 책 전체에서 그대로 씁니다. 표기에 한자가 남은 항목(郝장화)이나 일반 단어(公司 → 회사)는 빨갛게 표시해 실수를 막습니다.
  • 이름 표기 방식: 한자음(左京 → 좌경)과 현지 발음 중 고를 수 있고, 책 전체에 같은 방식을 적용합니다.
  • 인명·용어 자동 추출: 번역 전에 원문에서 자주 나오는 후보 목록만(본문은 보내지 않음) 한 번 보내 이름 표기를 정합니다. 요청 1회, 보통 몇 초입니다.
  • 문장부호 정리(결과 파일에만 적용): 。→. ，、→, 「」→" " ・→· 〜→~, 전각 숫자→반각, 3．5 → 3.5. 번역 요청에는 영향이 없어 다시 번역하지 않아도 됩니다.
  • 인코딩 자동 판별: UTF-8 · UTF-16 · GB18030(간체) · Big5/CP950(번체) · Big5-HKSCS · CP932/Shift-JIS · EUC-JP · Windows-1252를 비교해 가장 자연스러운 글자가 나오는 쪽을 고릅니다. 이상한 바이트 한두 개 때문에 전체가 깨지지 않게 그 글자만 대체합니다.
  • 원문 정리: 70자 안팎마다 줄이 바뀐 영어(구텐베르크·PDF)는 파일 전체가 그런 모양일 때만 문단으로 이어 붙이고, 아오조라 문고 주석(［＃改ページ］)·URL·이메일·코드는 번역하지 않고 그대로 둡니다.

G. 한계 — 프로그램이 해결할 수 없는 것

  • 번역 품질의 상한은 모델이 정합니다. 프로그램은 빠짐·거부·형식 오류를 걸러 내고 다시 시키지만, 문장을 더 잘 쓰게 만들 수는 없습니다. Flash Lite 같은 저가 모델이나 작은 로컬 모델은 문장이 어색하거나 지침을 덜 따르는 일이 더 많습니다.
  • 정책 차단은 엔진마다 다릅니다. 원문을 고쳐 차단을 피하지 않으므로, 한 엔진이 끝까지 막는 문단은 다른 엔진이 있어야 번역됩니다.
  • 막힘이 많은 글은 오래 걸립니다. 막힌 구간을 좁혀 가는 데 요청이 여러 번 필요하고, 요청마다 간격을 지켜야 합니다.
  • 같은 원문이라도 매번 똑같이 번역되지는 않습니다. 이름처럼 반드시 같아야 하는 것은 확정 용어집에 적어 두세요.
  • 무료 키는 한도가 낮습니다. 한도에 닿으면 기다리거나 다른 프로젝트의 키, 다른 엔진을 써야 합니다.
  • PDF · EPUB은 글자만 옮깁니다. 스캔 PDF의 문자 인식(OCR)이나 EPUB 복제 방지(DRM) 해제는 하지 않고, 2단 편집 · 표 · 각주가 많은 PDF는 글 순서가 섞일 수 있습니다. 원본 PDF · EPUB의 모양은 결과에 남지 않습니다.
